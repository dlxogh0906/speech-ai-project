## 4. sampling / weighting 구현

**방식: 발화 단위 loss 가중**(요청 우선순위 1). 행 복제를 늘리지 않으므로 문항·화자 반복이 늘지 않는다.

- `train_w2vbert_ctc.py --weights <파일>` — 행마다 가중치 한 줄. CTC loss 를 직접 계산해
  `Σ wᵢ·(ctcᵢ / lenᵢ) / Σ wᵢ` 로 합친다. HF 내장 loss(`reduction='mean'` = `mean(ctcᵢ/lenᵢ)`)와 같은 식에
  가중만 얹은 것이다.
- **검증**: 실제 배치 8개에서 가중치 전부 1 → HF 내장 loss 1.316005 와 **차이 0.00e+00**.
  첫 행만 2 → 1.254419 로 바뀜. 20 step 학습·검증·저장까지 정상.
- **H0 도 같은 경로(가중치 전부 1)로 돌린다** — 실험 간 달라지는 것은 가중치 파일뿐이다.
  `--weights` 를 주지 않으면 예전 코드 경로 그대로다.

**범주**(`scripts/data/build_stage2_weights.py`, TAG↔canonical 정렬):

| 범주 | 정의 | 학습 행 비율 |
|---|---|--:|
| insertion | 표준발음에 없는 소리가 끼어듦 | 4.11% |
| hard_pair | 같은 계열 세기 차이 자음 대치 11쌍 | 8.74% |
| vowel | 모음 자리에서 다른 모음으로 대치 | 7.10% |

겹침: 삽입∩쌍 12,661 · 삽입∩모음 13,467 · 쌍∩모음 16,419 · 셋 다 2,929행.

**hard_pair 11쌍** — 요청 6쌍(ㅅ→ㅆ · ㅆ→ㅅ · ㅈ→ㅊ · ㄱ→ㅋ · ㄸ→ㄷ · ㅉ→ㅈ) + **valid 에서 다시 뽑은** 5쌍
(ㄱ→ㄲ · ㅋ→ㄱ · ㅍ→ㅂ · ㄷ→ㄸ · ㅂ→ㅍ; step_38000 의 replay10 valid 예측에서 표본 30+ · 되돌림 ≥0.60 인
자음쌍, `analysis/hard_pairs_from_valid.json`). **앞선 쌍 목록은 test 에서 뽑은 것이라 학습 설계에 쓰지 않았다.**
valid 에서도 되돌림 상위는 전부 "같은 계열 세기 차이"였다(ㅅ→ㅆ 0.92 · ㅆ→ㅅ 0.85 · ㄱ→ㄲ 0.83 · ㅈ→ㅊ 0.74).
쌍별 학습 행: ㄱ→ㅋ 27,099 · ㅉ→ㅈ 22,046 · ㄸ→ㄷ 20,880 · ㅈ→ㅊ 20,342 · ㅋ→ㄱ 15,004 · ㅅ→ㅆ 14,952 ·
ㅆ→ㅅ 12,633 · ㄱ→ㄲ 11,505 · ㅂ→ㅍ 8,876 · ㅍ→ㅂ 5,430 · ㄷ→ㄸ 5,092.

**vowel** — 모음 대치 전체에 같은 가중(특정 모음만 더 주지 않는다: 표본 작은 항목 과가중 방지).
약했던 모음의 학습 행: ㅗ 18,372 · ㅡ 13,334 · ㅜ 12,276 · ㅛ 9,110.

**가중식** — `w = min(w_max, 1 + b·[삽입] + b·[쌍] + b·[모음])`, b = 0.5 · w_max = 2.0. 원어민 행은 항상 1.

| 실험 | 평균 w | 최대 w | w>1 행 | 실효 비중 삽입 / 쌍 / 모음 | 문항 최대 배율 | 화자 최대 배율 |
|---|--:|--:|--:|---|--:|--:|
| H0 | 1.000 | 1.0 | 0% | 4.1% / 8.7% / 7.1% | 1.00 | 1.00 |
| H1 삽입 | 1.021 | 1.5 | 4.1% | **6.0%** / 8.9% / 7.3% | 1.47 | 1.47 |
| H2 쌍 | 1.044 | 1.5 | 8.7% | 4.3% / **12.6%** / 7.3% | 1.23 | 1.44 |
| H3 모음 | 1.036 | 1.5 | 7.1% | 4.3% / 8.9% / **10.3%** | 1.23 | 1.45 |
| H4 셋 다 | 1.099 | 2.0 | 17.7% | **6.2% / 12.6% / 10.4%** | 1.36 | 1.82 |

"배율" = 그 문항(화자)이 학습에서 차지하는 몫이 가중 전 대비 몇 배가 됐나. 최대 1.82배로 과도한 쏠림은 없다.
가중 강도는 b=0.5 한 가지로 시작한다(요청 범위 1.25~2.0 의 중간). 강도 탐색은 H4 결과를 본 뒤 정한다.

**동일 조건**: 초기 checkpoint `w2vbert_stage1/step_10000` · lr 1e-5 · 40k step · tri-stage ·
**마스킹 꺼짐**(`apply_spec_augment=False` — step_38000 도 같다. 2026-09-28 확인, "mask 0.5" 는 config 값일 뿐 적용되지 않았다) ·
batch 1.6M 샘플 × accum 4 · 2k 간격 저장 · seed 42 — 전부 기존 Stage 2 와 같다. 바뀌는 것은
매니페스트(hold-out)와 가중치 파일뿐.

**step 선택**(`scripts/eval/select_holdout_ckpt.py`, valid 만 사용): 16k~40k 를 4k 간격으로 valid·valid_unseen 채점 →
제약 "valid_unseen 정상자리오류 ≤ 기준 + 0.2%p"(H0 은 자기 최솟값, H1~H4 는 H0 선택값) 안에서
valid_unseen MDD F1 최대. UER 은 쓰지 않는다. 종합 점수를 만들지 않고 step 별 표를 함께 남긴다.

## 9. Seen vs unseen prompt

H0 (문항 hold-out 으로 학습 · step 4k) — **같은 화자 조건(처음 보는 화자)에서 문항만 다르다**:

| | seen 문항 | unseen 문항 | 차이 | 참고: A 의 같은 두 문항셋 차이(A 는 둘 다 봤음) |
|---|--:|--:|--:|--:|
| MDD F1 | 0.426 | 0.237 | −0.189 | −0.063 (문항 구성 효과) |
| 헛지적 | 4.38% | 12.94% | ×2.95 | ×0.97 |
| JER | 7.23% | 16.37% | ×2.26 | ×1.01 |
| 되돌림 | 43.6% | 33.0% | −10.6%p | +5.2%p |
| 제3오류 | 12.3% | 20.6% | +8.3%p | +0.6%p |

- F1 하락 −0.189 중 약 −0.063 은 문항 자체가 어려워서다(A 도 같은 폭으로 떨어진다). **나머지 약 −0.13 이
  "문항을 못 봐서" 생긴 손실**이다.
- **헛지적은 문항 구성으로 설명되지 않는다**(A 는 두 셋에서 2.26% vs 2.19% 로 같다). H0 의 ×2.95 는 그대로
  일반화 실패다. valid 에서도 16.7~24.8% 로 같은 방향이었다.
- **되돌림은 오히려 준다.** 외운 문장이 없어 표준발음으로 덮지 않는 대신 제3오류(엉뚱한 소리로 적기)가 늘어난다.
  `17` 의 문단(RP) 평가, `08` 의 300m 홀드아웃과 같은 모습 — 이번에는 길이·과제가 같은 조건에서 확인됐다.

## 14. 최종 판단

H4 가 끝나면 작성한다. H0 만으로 답할 수 있는 것:

1. **문항 hold-out 을 하면 얼마나 떨어지나?** — F1 0.426 → 0.237(−0.189, 문항 구성 효과 −0.063 을 빼면 약 −0.13),
   **헛지적 4.4% → 12.9%(×3)**. 헛지적이 핵심이고, 학습을 오래 할수록 커진다.
7. **개선이 인코더에서 나온 것인가, 보정기에서 나온 것인가?** — 보정기(B·D)는 본 문항에서만 효과가 있고
   처음 보는 문항에서는 정밀도가 절반이 된다(0.665 → 0.304). **문장 일반화는 보정기로 풀 수 없다.**

H4 로 답할 수 있는 것:

2. **hard-example 가중이 unseen 에서도 개선되나?** — 보존·되돌림은 unseen 에서도 같은 방향(+1.7%p / −2.2%p)이지만
   F1 은 그대로(0.237 → 0.234), 헛지적은 +0.8%p. **문장 일반화 자체는 개선되지 않는다.**
3. **어떤 오류가 가장 개선되나?** — 특정 자음쌍: ㅅ→ㅆ(보존 9.0 → 33.6%), ㄱ→ㅋ(35.6 → 50.6%), ㄱ→ㄲ(7.6 → 16.6%).
4. **ㅅ→ㅆ · ㅈ→ㅊ · ㄱ→ㅋ 보존율이 올랐나?** — ㅅ→ㅆ·ㄱ→ㅋ 는 **크게 올랐다**. ㅈ→ㅊ 는 15.9 → 17.4% 로 작다.
5. **삽입 재현율이 개선됐나?** — seen 0.333 → 0.339 로 **사실상 아니다**. unseen 0.380 → 0.422(표본 287).
6. **헛지적이 늘지 않았나?** — **늘었다.** seen 4.38 → 4.83%, unseen 12.94 → 13.76%.
8. **step_38000 을 교체할 근거가 충분한가?** — **아니다.** H0·H4 는 문항 24개를 빼고 학습한 실험 모델이고,
   선택된 4k step 은 본 문항 성능이 A 보다 낮다(F1 0.42 vs 0.50, 헛지적 4.4~4.8% vs 2.3%).
   얻은 것은 **"가중이 특정 쌍을 크게 개선한다"는 근거**다 — 전체 문항 학습에 이 가중을 적용할지는 스크리닝 뒤에 정한다.

데이터 자체다 → 다음 후보는 문장 다양성(의사라벨·합성 오발음)이다.

### P5 — 의사라벨로 문장 다양성 추가 (2026-09-30)

AIHub 131 외국인 읽기 발화(`manifest_505_weak_v1` 풀)에 **H0 4k 의 그리디 전사**를 라벨로 붙여 학습 오디오의 25% 로 섞었다
(`scripts/data/build_pseudo_labels.py` → `build_p5_manifest.py`). hold-out 24문항이 부분 문자열로 든 문장은 모두 뺐다(9,636발화).
교사를 H0 로 한 이유: step_38000 은 hold-out 문항을 학습해 누출 의심을 피할 수 없다.

**라벨 품질을 먼저 쟀다** — 같은 교사·필터를 정답이 있는 valid_unseen 문장(RS)에 돌린 결과:

|---|--:|--:|

### SupCon 오프라인 탐침 (2026-10-01)

질문: 인코더 표현 안에 세기 차이(ㅅ/ㅆ · ㄱ/ㅋ …)를 가를 정보가 **이미 있는데 CTC 헤드가 못 쓰는 것**인가?
그렇다면 CTC+SupCon 결합 학습에 기대할 게 있다.

방법(`scripts/eval/extract_phone_embeddings.py` → `scripts/score/probe_supcon_offline.py`): 인코더 고정(H0·H4 4k),
TAG 를 CTC 강제정렬해 세기 계열 자음 14개의 구간 임베딩(±1 프레임 평균)을 뽑는다. train 3만 발화(87,582구간)로 학습,
valid(본 문항 28,700구간)·valid_unseen(처음 보는 문항 24,236구간)로 평가. 네 가지 비교:
head(CTC 헤드 그대로) · head_lr(헤드 출력 재보정) · emb_lr(임베딩 위 선형) · supcon(임베딩 → SupCon 투영 → 선형).
지표는 **쌍별 AUC** — 표준 자모 c 인 자리에서 "실제 a 로 말함" vs "c 로 말함"을 점수 log p(a) − log p(c) 로 가르는 정도.

H0 · 마지막 층(24) 쌍별 AUC:

| 쌍 | 본 문항 (오류 n) head / head_lr / emb_lr / supcon | 처음 보는 문항 (오류 n) head / head_lr / emb_lr / supcon |
|---|---|---|
| ㄱ→ㅋ | (127) 0.943 / 0.943 / 0.947 / 0.949 | (139) **0.837** / 0.851 / 0.790 / 0.792 |
| ㄱ→ㄲ | (58) 0.900 / 0.900 / 0.893 / 0.895 | (85) **0.848** / 0.855 / 0.795 / 0.802 |
| ㅅ→ㅆ | (73) 0.881 / 0.884 / 0.873 / 0.885 | (109) **0.815** / 0.820 / 0.671 / 0.790 |
| ㅆ→ㅅ | (67) 0.803 / 0.803 / 0.811 / 0.802 | (156) **0.718** / 0.727 / 0.679 / 0.711 |
| ㅈ→ㅊ | (102) 0.871 / 0.883 / 0.889 / 0.900 | (49) **0.757** / 0.764 / 0.708 / 0.757 |
| ㄸ→ㄷ | (104) 0.829 / 0.833 / 0.814 / 0.828 | (42) **0.698** / 0.698 / 0.655 / 0.642 |

(중간 층 16 도 같은 모습이거나 더 나쁘다. H4 도 같다. 전체 표: `analysis/supcon_probe/*_probe_L{16,24}.json`.)

**읽는 법**

1. **본 문항에서 네 방법이 거의 같다**(차이 0.00~0.03). 헤드 출력을 재보정해도(head_lr) 거의 안 오른다 —
   **CTC 헤드가 이미 표현에서 뽑을 수 있는 만큼 쓰고 있다.**
2. **처음 보는 문항에서는 임베딩 분류기가 헤드보다 나쁘다**(ㅅ→ㅆ 0.815 → 0.671). 본 문항 데이터로 학습한 분류기가
   문장 맥락에 기대는 단서를 배워 새 문장에서 무너진다 — 문장 일반화 문제의 축소판이다.
3. **같은 쌍이라도 처음 보는 문항에서 분리도 자체가 낮다**(ㄱ→ㅋ 0.943 → 0.837, ㅅ→ㅆ 0.881 → 0.815).
   표현이 문장 맥락에 묶여 있다 — 헤드가 아니라 **표현(인코더)이 새 문장에서 약하다.**
4. **H4 가중은 ㄱ→ㅋ 의 분리도 자체를 올렸다**(처음 보는 문항 head AUC 0.837 → **0.922**). 반면 ㅅ→ㅆ 는 AUC 가
   거의 그대로(0.815 → 0.818)인데 보존은 9 → 34% 로 올랐다 — **ㅅ→ㅆ 개선은 판정 기준이 옮겨간 것**이지
   구별력이 좋아진 것이 아니다. 이런 쌍은 쌍별 임계값(보정기)으로도 같은 효과를 낼 수 있다(확인되지 않음).
   → **10-03 쌍별 임계값 실험으로 일부 정정**: AUC 는 같지만 헛지적이 낮은 구간에서는 H4 가 실제로 낫다(아래 절).

**판정**: 탐침의 전제("표현에 정보가 있는데 헤드가 못 쓴다")가 **성립하지 않는다.** 고정 인코더 위 SupCon 은 새 문장에서
헤드보다 나쁘다. → **CTC+SupCon 결합 학습은 우선순위를 내린다.** (한계: 결합 학습은 인코더 자체를 바꾸므로 이 탐침이 결과를
완전히 예측하지는 못한다. SupCon 설정은 한 가지만 시험했다. 처음 보는 문항의 쌍별 오류 표본이 30~156개라 AUC 차이 0.02 이하는
판단하지 않는다.)

**종합**: 문장 일반화의 병목은 헤드도 판정도 아니라 **인코더 표현이 새 문장 맥락에서 약한 것**이고, 그 표현을 바꾸는 검증된 길은
학습 데이터(외국인 억양 × 새 문장 × 깨끗한 라벨)다 → 사람 TAG 파일럿(`docs/05_사람TAG_라벨링_파일럿_설계.md`)이 1순위.
H4 가중은 특정 쌍(ㄱ→ㅋ 등)의 구별력을 실제로 올리므로 유지한다.

### 쌍별 임계값 오프라인 실험 (2026-10-03)

질문: H4 가중의 쌍별 개선을 **재학습 없이 판정 기준(임계값)만 쌍마다 옮겨서** H0 로 따라잡을 수 있나.
SupCon 탐침이 저장한 자리별 로그확률(H0 · H4, valid · valid_unseen)만 썼다 — GPU 불필요.
점수 s = log p(실제로 낼 법한 자모 a) − log p(표준 자모 c). 임계값은 **valid(본 문항)에서 F1 최대로 고르고** valid_unseen 은 한 번만 봤다.
스크립트 `scripts/score/pair_threshold_offline.py` · 결과 `$MDD_OUTPUTS/analysis/supcon_probe/pair_threshold.json`.

처음 보는 문항 — 보존(오류 재현율) / 헛지적률(실제 c 인 자리를 a 로 지적):

| 쌍 | 오류 · 정상 자리 | H0 τ=0 | H0 쌍별 τ | H4 τ=0 | 같은 헛지적에서 보존 H0 → H4 |
|---|---|---|---|---|---|
| ㅅ→ㅆ | 109 · 2,888 | 14.7% / 3.4% | 45.9% / 12.3% | 45.9% / 11.2% | 5%: 16.5 → **33.0%** · 11.2%: 39.4 → 45.9% |
| ㄱ→ㅋ | 139 · 4,654 | 52.5% / 14.9% | 56.1% / 17.8% | **71.9% / 8.9%** | 5%: 33.8 → **51.8%** · 8.9%: 41.7 → **71.9%** |
| ㄱ→ㄲ | 85 · 4,654 | 36.5% / 4.3% | 43.5% / 8.5% | 43.5% / 6.7% | 5%: 36.5 → 37.6% · 6.7%: 38.8 → 43.5% |
| ㅈ→ㅊ | 49 · 2,029 | 30.6% / 4.4% | 63.3% / 25.1% | 30.6% / 3.0% | 5%: 34.7 → 38.8% |

(τ=0 은 두 자모 중 높은 쪽 — 모델 기본 판정의 대용이고 그리디 전사와 같지는 않다. "같은 헛지적에서 보존" 은 처음 보는 문항에서
H0 의 임계값을 H4 와 같은 헛지적률이 되게 옮겨 잰 **분석용 비교**다 — 임계값 선택에는 쓰지 않았다.)

**읽는 법**

1. **ㅅ→ㅆ: 임계값만으로 대부분 따라잡지만 전부는 아니다.** H0 에 쌍별 τ(−1.1)를 주면 보존이 14.7 → 45.9% 로 H4 와 같아진다
   (헛지적은 12.3% 로 H4 보다 1.1%p 많다). 그러나 같은 헛지적에서 비교하면 H4 가 낫고, **헛지적이 낮은 구간(5%)에서는 2배**다
   (16.5 → 33.0%). AUC 가 같은 것은 곡선 전체를 평균한 값이라서다 — **H4 는 서비스가 쓰는 낮은 헛지적 구간을 실제로 끌어올렸다.**
   앞 절의 "ㅅ→ㅆ 개선은 판정 기준이 옮겨간 것" 은 높은 헛지적 구간에서만 맞다.
2. **ㄱ→ㅋ: 임계값으로는 못 따라간다.** 같은 헛지적 8.9% 에서 41.7 → 71.9%. 인코더가 실제로 더 잘 가른다(AUC 0.837 → 0.922).
3. **ㅂ→ㅃ 은 H4 에서 나빠졌다**(같은 헛지적 5% 에서 25.0 → 16.7%, τ=0 헛지적 1.4 → 10.3%). 다음 가중 학습에서 이 쌍을 빼거나 따로 본다.
4. **ㄷ 계열은 이미 잘 가른다** — 손댈 필요 없다.

**판정**: 쌍별 임계값은 **재학습 없이 쓸 수 있는 손잡이**다 — ㅅ→ㅆ 보존을 15 → 40% 대로 올릴 수 있다(대가: 그 자리 헛지적 3 → 11~12%).
그러나 **H4 가중을 대신하지는 못한다** — 같은 헛지적에서 ㅅ→ㅆ · ㄱ→ㅋ · ㅂ→ㅍ 는 H4 가 낫다. → H4 가중 유지(ㅂ→ㅃ 제외 검토),
임계값은 최종 인코더 위 보정기 단계에서 쌍별로 운영점을 정하는 데 쓴다.

**한계**: 자리 구간을 **실제 발음(TAG)에 강제정렬**한 값이다 — 서비스는 표준발음에 정렬하므로 이 결과는 분리 가능성의 상한에 가깝다.
처음 보는 문항의 오류 표본이 쌍마다 30~139개라 보존율 차이 ±8%p 안쪽(ㄱ→ㄲ · ㅈ→ㅊ · ㅂ→ㅍ · ㅂ→ㅃ)은 흔들림일 수 있다.
