## 1~3단계 속도 — 인코더 forward (발화 1건)

단독 실행(01:33~01:43, load 2.6 에서 시작). CPU 는 `taskset` 으로 코어를 묶어 작은 인스턴스를 흉내 냈다.

|---|--:|--:|--:|

- **속도 이득의 대부분은 ONNX 변환에서 나온다.** int8 은 그 위에 3~14% 만 더한다(국적 모델에서 본 것과 같은 경향 —

- 4코어 인스턴스에서 6초 발화 0.75초 — 서비스 체감으로 충분하다. 메모리 1.1 GB 라 4 GB 머신에 워커 2~3개가 들어간다
  (PyTorch 는 워커당 3.3 GB).
- VNNI/AMX 가 있는 최신 인텔 CPU 에서는 int8 이득이 더 클 수 있다 — 여기선 재지 못했다.

### GPU — A100

| 발화 | PyTorch fp16 (현재) | ONNX fp32 (CUDA) | **ONNX fp16 (CUDA)** |
|--:|--:|--:|--:|
| 3초 | 16.4 ms | 10.1 | **6.9** |
| 6초 | 17.0 ms | 11.3 (1.50×) | **7.5 (2.27×)** |

## 동시 요청 처리량 (2026-09-16 추가)

`09_추론속도.md` 는 **PyTorch** 기준이다. 경량화본으로 다시 쟀다 — 서빙 진단 경로 전체(`analyze`: 인코더 + 강제정렬 + 특징)를

|---|--:|--:|
| CPU int8 · 8워커 × 2스레드 | **5.25 req/s** | 약 1.5 s |

- **워커를 무작정 늘리면 느려진다.** GPU 는 3워커가 6워커보다 38% 빠르고, CPU 는 8워커가 상한이다.

- 이 값은 오프라인 파이프라인이다. 실제 API 는 HTTP 업로드·오디오 디코딩이 더해지므로 **부하 테스트로 다시 확인해야 한다.**

**용량 환산** (발화 6초 기준)

| 상황 | CPU 16코어 1대 | GPU 1장 |
|---|---|---|
| 100건 동시 도착 | 전부 처리에 19초, 마지막 사용자 대기 19초 | **2.7초** |
| 100건 동시 도착을 2초 안에 | 서버 약 10대 | 1장이면 충분 |

- **초당 10건을 넘어가면 GPU 1장이 CPU 여러 대보다 싸다.** 저가 GPU(T4·L4)는 아직 재지 못했다 — A100 대비 3~5배 느리다고 봐도 CPU 여러 대보다 낫다.

### 실제 API 로 잰 값 (2026-09-16) — 위 표는 오프라인, 이건 HTTP

`deploy/mdd-api` 에 ONNX 를 붙여 **다른 포트(8916)** 로 띄우고, 기존 PyTorch(8917)와 같은 발화를 보내 대조했다.

- 교체 방법: `MDD_SERVE_ONNX=<onnx>` (+ `MDD_SERVE_DEVICE=cpu|cuda`, `MDD_SERVE_THREADS`), 비우면 기존 PyTorch 경로.
  인코더 forward 만 ONNX 세션으로 바꾸고 진단·정렬·점수 코드는 그대로다. 회귀기도 그대로 쓴다.
- **응답 동일성: 20발화 전부 인식 자모열과 지적 목록이 같다**(6워커에서도 동일). 세션 점수 차이 ≤0.01점.
- 요청 1건(부하 없음): GPU PyTorch 0.13 s · CPU int8 1.0 s(4스레드) / 1.9 s(2스레드, 7.6초 발화).
  이 중 오디오 디코딩(ffmpeg)은 0.03 s 로 무시할 수준이다.

| 1워커 × 4스레드 | 2.7 req/s | — | — | 1.2 GB |
| 6워커 × 2스레드 | 3.4 req/s | — | — | ~10 GB |
| **8워커 × 2스레드 (권장)** | **4.07 req/s** | 3.99 req/s | 700% / 1600% | **13.7 GB** |
| 12워커 × 1스레드 | 3.82 req/s | 4.13 req/s | 1,200% / 1600% | 21.1 GB |

- **처리량 ≈ 워커 수 ÷ 요청당 지연.** 워커를 8→12 로 늘려도 4 req/s 근처에서 평평하다(메모리만 1.5배).
- 한 프로세스 안에서는 동시 처리가 GIL 에 막힌다 — 인코더(ONNX)는 GIL 을 놓지만 강제정렬·GOP·점수는 파이썬·numpy 다.
  그래서 **스레드가 아니라 워커 프로세스를 늘려야** 한다.
- HTTP 경로는 오프라인 처리량(5.25 req/s, 5.8초 발화)의 약 80% 다. 나머지는 업로드·스레드풀·요청당 파이썬 작업이다.
- ⚠️ **워커를 늘리면 `/session` 점수가 갈라진다** — 세션이 프로세스 메모리에 있다. 같은 세션을 같은 워커로 보내거나(스티키)
  공용 저장소로 옮기기 전까지 `--workers` 는 단발 `/diagnose` 전용이다.
- ⚠️ 워커당 RSS 가 1.7 GB 다(int8 단독 1.1 GB 보다 크다) — API 가 여전히 torch·fairseq 를 import 한다.
  완전히 떼어내려면 사전 로딩과 `ctc_loss` 를 numpy 로 바꿔야 한다.

## 판단

| 서빙 환경 | 권고 | 근거 |
|---|---|---|
| **CPU** | **ONNX int8(동적 · 텐서별)** | 정확도·점수 차이 없음(TAG · LAR · 원어민 PER), 1.5~1.8배 빠름, 메모리 1/3. 원어민 발화는 출력 흔들림이 더 크다(동일 77%) |
| **GPU** | **ONNX fp16** | 정확도·점수 차이 없음(TAG · LAR · 원어민 모두 출력 ≥98.75% 동일), 2.3배 빠름, 파일 1/2 |
| 기각 | int8 채널별 · int8 정적 QDQ | 오류 F1 −0.004 / 출력 붕괴 |

국적 모델(KD 인코더)은 반대 결론이다 — int8 에서 top-1 이 유의하게 −1.4%p 떨어지고 속도 이득이 없어 fp32 를 유지한다
(`tasks/nationality-classification/results/09_KD인코더_int8.md`).

**아직 서빙에 붙이지 않았다.** `deploy/mdd-api` 는 PyTorch `Decoder` 를 쓴다. ONNX 로 바꾸려면 `forward_lprobs` 자리에
세션을 끼우면 되고(`eval_score_backend.py` 의 ort 백엔드가 그 방식으로 서빙 `analyze` 를 그대로 태웠다), 교체 전에
다른 포트로 띄워 응답을 대조한다(CLAUDE.md). 점수 회귀기는 **바꾸지 않아도 된다**(위 보존 결과).

## 4단계 — 12층 학생 + 지식증류

- 학생: 교사 24층 중 **홀수층(1,3,…,23)** 12개 → 1.64억 파라미터(52%) · 0.61 GiB. 기존 로더로 그대로 읽힌다.
  학습 전 조합 비교(실발화 100개, 교사 대비 토큰 편집률): 홀수층 17% · 짝수층+23 22% · 하위6+상위6 56% · 상위12층 92%.
- 학습: CTC + KL(T=2, α=0.3, blank 프레임 가중 0.5) + 층별 은닉 코사인(β=0.5), 재구성 TAG train 143만 발화,
  계획 40,000 → **실제 24,000 업데이트**(max_tokens 1.6M × 4, 아래 경과 참고), valid 3천 발화로 2천 업데이트마다 검증. 2026-09-15 01:43 ~ 13:46.
- ⚠️ **데이터 한계**: 교사는 TAG + 무오류 LAR 3.9만(38,979)×3 + 원어민 자유대화 5.37만×2 로 학습됐는데, 이 서버엔 TAG 만 있다.
  학생은 **원어민·LAR 도메인에서 교사보다 나빠질 수 있고, 여기선 그걸 잴 데이터도 없다**(원어민 PER 게이트 측정 불가).
- 층을 바꾸면 GOP 특징이 달라지므로 **점수 회귀기는 다시 학습해야 한다**(체크포인트와 짝).

- 경과(valid 3천 발화 PER, 교사 0.0474): 2k 0.0888 · 4k 0.0687 · 6k 0.0623 · 8k 0.0581 · 10k 0.0570.
- 03:45 부터 같은 GPU 에서 다른 MDD 학습 2개가 돌기 시작해 속도가 1.33 → ~0.4 업데이트/초로 떨어졌다.
  **40k 대신 24k 업데이트로 줄였다** — 24k 의 tri-stage 감쇠가 정확히 12k 에서 시작하므로 12k 체크포인트에서 이어 붙였다.
