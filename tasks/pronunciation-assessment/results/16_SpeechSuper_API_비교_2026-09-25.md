# SpeechSuper ↔ 자체 발음평가 API 비교 (2026-09-25)

발음 총점은 비교적 가깝지만, 유창성·종합 점수·세부 음소 점수·입력 거절 동작에는 차이가 있다. 전체적으로 동등하다고 판단하기는 어렵다.

> **2026-09-26 후속 점검에서 이 문서의 결론 세 가지가 바뀌었다 — 맨 아래 「후속 점검」 절을 먼저 볼 것.**
> 유창성 지표 해석, 글자 매핑 「개선 대상」 판정, null 음소 처리 판정이 모두 정정됐고 문장 점수 눈금이 바뀌었다.

## 방법

- 저장된 웹마이크 녹음 130건 중 16 kHz / mono / PCM 16bit, 1~20초 파일을 대상으로 중복 오디오 SHA256을 제거했다.
- 저장 당시 자체 발음 점수 순으로 정렬하고 균등 간격으로 30건(12개 기준 문장)을 선택했다. 무작위 대표 표본이 아니라 점수 범위를 넓힌 탐색 표본이다.
- 같은 WAV 바이트와 같은 refText를 두 API에 보냈다. 요청은 순차 실행했다.
- SpeechSuper: https://api.speechsuper.com/sent.eval.kr, 자체: http://127.0.0.1:8932/sent.eval.kr.
- SpeechSuper 제공 키로 정상 채점 확인. 원본 응답 저장 시 인증 params와 applicationId를 제거했다.
- 자체 모델은 현재 실행 서버(w2vbert stage2 step_38000). 인식 실패 점수 null 수정 적용 후 측정했다.
- 양쪽 점수가 있는 27건으로 점수 차이를 계산했고, 자체 HTTP 400인 3건은 별도 기록했다. 0점은 유효한 값이며 null과 구분했다.
- 동일 화자가 반복했을 수 있는 소규모 녹음이며 원어민/외국인·정답 점수 라벨이 없어 정확도 우열이나 서비스 전체의 동등성을 판단할 수 없다.

## 응답 스키마 차이

- 자체 글자 점수는 words[].score, 이번 SpeechSuper 응답은 words[].scores.pronunciation 및 scores.overall이다.

- SpeechSuper 응답에는 integrity/speed 등이 있고 자체 응답에는 actual_jamo/readType/comprehensibility 등이 있다. 이번 SpeechSuper 응답에는 자체와 동일한 readType/actual 필드가 없어 판정 일치율을 직접 산출하지 않았다.
- 따라서 주소만 바꾸면 모든 응답 필드가 완전히 호환된다는 기존 API 문서 문구는 실제 응답과 맞지 않는다. 사용하는 클라이언트 필드별 매핑이 필요하다.

### 추가 확인: 음소 출력 차이

저장된 응답만 재분석했다. 외부 API 추가 호출은 없다.

양쪽 채점 성공 27건의 글자 364개 중 82개(22.5%)에서 글자에 묶인 한글 음소열이 달랐다.
점수 유무와 무관한 글자 수이므로 위 점수 비교의 355쌍과 분모가 다르다.
문장 전체 음소열을 이어 붙이면 완전히 같은 녹음은 10/27건이다.
따라서 차이는 기호 표기뿐 아니라 글자 경계 및 음소열 자체에도 있다.

| 구분 | 자체 API | SpeechSuper 실측 응답 |
|---|---|---|
| ㅏ 표기 | alpha=aa, alpha_jamo=ㅏ | phoneme=A, alpha=ㅏ |
| 초성 ㄴ / 받침 ㄴ | nn / nf | N / N2 |
| 인식된 소리 | actual, actual_jamo | 같은 역할을 명시한 별도 필드 없음 |
| 오류 설명 | errorType, 글자 readType | 이번 응답에는 해당 필드 없음 |
| 음소 시간 구간 | 없음 | span.start, span.end |

SpeechSuper의 alpha를 자체 actual_jamo와 같은 의미의 자유 인식 결과라고 단정할 수 없다.
이번 비교의 한글 음소열은 자체 alpha_jamo와 SpeechSuper alpha를 대조한 것이다.

**글자 경계 차이 사례:**

| 기준 문장 일부 | 자체 글자별 음소 | SpeechSuper 글자별 음소 |
|---|---|---|
| 값이 | 값=ㄱㅏㅂㅆ / 이=ㅣ | 값=ㄱㅏㅂ / 이=ㅆㅣ |
| 었습 (피었습니다) | 었=ㅓㄷㅆ / 습=ㅡㅁ | 었=ㅓㄷ / 습=ㅆㅡㅁ |
| 겠다 | 겠=ㄱㅔ / 다=ㄷㄸㅏ | 겠=ㄱㅔㄷ / 다=ㄸㅏ |

위 부분은 이어 붙인 음소열은 같고 소리가 어느 글자에 속하는지만 다르다.
자체 map_to_words는 철자 자모와 표준발음 자모를 편집거리로 정렬하고 소유 글자를 할당한다.
이 과정에서 연음된 초성이나 경음화된 소리가 앞 글자에 묶이거나 받침이 다음 글자로 넘어가는 사례가 확인된다.
이 묶음으로 글자 점수까지 계산하므로 단순 표시 차이로 끝나지 않는다. 자체 글자 매핑의 개선 대상이다.

**음소열 자체 차이 사례:** 일부 녹음에서 자체 '학'=ㅎㅏㄱ / SpeechSuper '학'=ㅏㄱ,
자체 '찍'=ㅉㅣㄱ / SpeechSuper '찍'=ㅉㅣㅋ 등이 나온다.
같은 문장에서도 SpeechSuper 반환열이 녹음에 따라 달라지는 사례가 있어 고정 기호 치환만으로 해결할 수 없다.
누가 실제 소리를 더 정확히 판정했는지는 청취·정답 라벨 없이 확정하지 않았다.

**null 처리의 영향:** 20260923-045726-317의 '었'은 자체 ㅓ=null, ㅆ=96으로 글자 점수가 96이다.
SpeechSuper는 ㅓ=0, ㄷ=10이며 글자 점수 2다. 음소 구성도 다르지만,
자체 평균에서 null을 제외하는 정책 때문에 일부 음소만 채점된 글자도 높게 보일 수 있다.
actual_jamo=null만으로 마이크 인식 실패와 실제 발음 누락을 구분할 수는 없다.
이 조사는 동작을 확인한 것이며 점수 정책이나 운영 코드는 변경하지 않았다.

## 정정 1 — 유창성은 문장 단위로 쓸 수 있다

이 문서와 그 전 논의에서 인용한 **「유창성 발화 단위 상관 −0.03」은 계산 오류다.**

| | 라벨이 붙어 있는 비율 |
|---|--:|
| 발음·이해 | 전체 발화의 100% |
| **유창성** | **23.6% — 문장(RS)에만 있고 단어(RW) 13.6만 건에는 없다** |

라벨 없는 단어 발화를 0점으로 넣고 계산해 상관이 뭉개졌다. 라벨이 있는 발화만으로 다시 재면:

| 차원 | 발화 단위 | 화자 단위 | 표본 |
|---|--:|--:|--:|
| 발음 | 0.433 | 0.674 | 177,969 |
| 이해 | 0.433 | 0.691 | 177,969 |
| **유창성** | **0.610** | **0.763** | 42,044 |

**유창성이 셋 중 가장 정확하다.** 따라서 「종합 산식에서 유창성을 빼자」·「객관 지표로 재정의하자」는
필요 없다. 참고로 객관 지표만 쓰면 오히려 낮다 — 쉼 비율 0.468 · 발화속도 0.503 · 속도+쉼 0.502(발화 단위).

## 정정 2 — 글자 매핑은 우리 결함이 아니다

「자체 map_to_words 의 개선 대상」으로 지목된 부분을 실제로 고쳐서(연음·경음화된 소리를 뒤 글자로 보내는
음절 기준 매핑) 저장된 30건으로 재측정했다.

| 방식 | SpeechSuper 와 글자 음소열이 같은 비율 |
|---|--:|
| 현재(철자 기준) | **77.5%** (282/364) |
| 음절 기준으로 변경 | 67.6% (246/364) |

**오히려 나빠져 되돌렸다.** 이유는 두 가지다.

- SpeechSuper 자체가 일관되지 않다 — `값이`는 소리 기준(값=ㄱㅏㅂ·이=ㅆㅣ), `꽃이`·`밥을`은 철자 기준(꽃=ㄲㅗㅊ·밥=ㅂㅏㅂ).
- 그쪽 `alpha` 에는 **실현형이 섞여 있다** — 학=ㅏㄱ(ㅎ 없음) · 먹=ㅁㅓㅇ · 공=ㄲㅗㅇ · 찍=ㅉㅣㅋ.
  우리 `alpha`(내야 할 소리)와 종류가 다른 값이므로 **일치율을 목표로 삼는 것 자체가 성립하지 않는다.**

조사 결과는 `src/mdd/speechsuper.py::map_to_words` 주석에 남겨 같은 시도를 반복하지 않게 했다.

## 정정 3 — null 음소를 0점으로 세면 안 된다

「누락을 평균에서 빼 점수가 부풀려진다」는 지적을 검증했다.

| 처리 | SpeechSuper 글자 점수와 평균 절대차 |
|---|--:|
| **현재(누락은 평균에서 제외)** | **13.3** |
| 누락 0점 | 14.0 |
| 누락 20점 | 14.0 |
| 누락 40점 | 14.2 |

어느 쪽으로 바꿔도 나빠진다. SpeechSuper 도 일관되지 않다 — 우리가 `문`의 ㅁ 을 놓친 3건에 **100점**을,
`었`·`진`에는 **2점**을 줬다. 누락 37건의 성격을 보면:

- 같은 자모가 잇달아 나는 자리 7건(19%) — 독립**문** [동님문] 의 `ㅁㅁ` 은 길게 한 번 난다.
- 파열음이 뒤 장애음에 먹히는 자리 다수 — 했**습**·마셨**습** [얻씀] 의 받침 `ㄷ`.

**대부분 학습자가 빠뜨린 것이 아니라 원래 그렇게 들리는 자리**이므로 0점 처리는 정확히 읽은 사람을 깎는다.
현재 정책(제외)을 유지하되, 화면에서는 「음소 1개 판정 못함」처럼 표시하는 편이 낫다.

## 변경 — 문장 점수 눈금을 백분위로 폈다

정정 1 로 정확도 문제가 아님이 확인됐으므로, 남은 차이는 **눈금**이었다.

원인: 사람 채점이 외국인 학습자 기준이라 평균 3.30/5 이고, 회귀 모델은 확신이 없으면 평균으로 붙는다.
실제 4.5~5.0점 발화에도 예측 평균이 **3.82**(유창성)·**3.55**(발음)다. 5점 만점 비례로 환산하면
**잘 읽어도 76점이 천장**이었다.

바꾼 방식: 예측값을 **학습자 분포에서의 백분위**로 환산한다(`scripts/score/calibrate_utt_percentile.py`
→ `score_phoneme/utt_percentile.json`). 순서는 그대로고 눈금만 넓어진다. **80점 = 학습자 상위 20%** 이므로
음소 점수(틀렸을 확률 기반)와 읽는 법이 같아진다. 표가 없으면 예전 방식으로 물러난다.

| 녹음 | 전(5점 비례) | **후(백분위)** | SpeechSuper |
|---|---|---|---|
| 학교에서 친구를 만났어요 (정확) | 종합 93 · 유창 83 · 이해 86 | **종합 98 · 유창 96 · 이해 99** | 종합 90 · 유창 99 · 이해 83 |
| 오늘 날씨가 참 좋네요 (정확) | 종합 92 · 유창 83 · 이해 81 | **종합 98 · 유창 95 · 이해 98** | 종합 99 · 유창 100 · 이해 91 |
| 값이 너무 비싸서 못 샀어요 (일부러 틀림) | 종합 75 · 유창 47 · 이해 46 | **종합 58 · 유창 8 · 이해 2** | 종합 87 · 유창 98 · 이해 74 |
| 꽃이 피었습니다 (일부러 틀림) | 종합 80 · 유창 58 · 이해 57 | **종합 55 · 유창 8 · 이해 2** | 종합 70 · 유창 92 · 이해 77 |

**남은 차이**: 일부러 틀리게 읽은 녹음에서 우리 유창성이 8점까지 떨어진다. 우리 유창성 예측이
「또렷하게 들리는가」에 크게 기댄 탓이다(중요도 1위 28%, 발화속도 25%). 발음만 흐려도 유창성이 같이 내려간다.
SpeechSuper 는 같은 녹음에 92~98점을 주어 발음과 유창성을 분리한다. **어느 쪽이 옳은지는 제품 판단이며 바꾸지 않았다.**
