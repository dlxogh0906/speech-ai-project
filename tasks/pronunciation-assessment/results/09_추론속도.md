# 09 — 추론 속도 측정 (2026-08-05)

서비스 탑재 가능한 응답 속도인지 판단하기 위한 실측. **8월 7일 GPU 사용 종료 전** 확보.

측정 대상은 배포 모델 `mdd_ckpt_tag_all_native/checkpoint_best.pt`.
마이크로벤치가 아니라 실제 서빙 경로(`deploy/mdd-api` 의 `analyze`)를 그대로 태웠다.

장비: A100 80GB ×1 · CPU 16코어. 재현은 `scripts/eval/bench_latency.py`.

---

## ① 발화 1건 지연

발화 길이별 중앙값(ms). 괄호는 실시간 배수 — 1초 오디오를 몇 배 빠르게 처리하는가.

| | 3초 | 6초 | 12초 |
|---|--:|--:|--:|
| **GPU (fp16)** | **21.8** (137배) | **28.2** (213배) | **40.9** (293배) |
| CPU 16스레드 | 294 (10.2배) | 561 (10.7배) | 986 (12.2배) |
| CPU 8스레드 | 358 (8.4배) | 632 (9.5배) | 1,258 (9.5배) |
| CPU 4스레드 | 665 (4.5배) | 1,259 (4.8배) | 2,572 (4.7배) |
| CPU 1스레드 | 1,857 (1.6배) | 3,625 (1.7배) | 7,531 (1.6배) |

**GPU 대비 CPU는 6초 발화 기준 20배(16스레드) ~ 45배(4스레드) 느리다.**

CPU 는 fp32, GPU 는 fp16 이다. `forward_lprobs` 가 `.half().cuda()` 로 박혀 있어
CPU 경로는 등가 fp32 구현으로 쟀다 — CPU 에서 fp16 은 느리거나 미지원이다.

## ② 병목

| 구간 | GPU 6초 | CPU 16스레드 6초 |
|---|--:|--:|
| 인코더 forward | 17.2 ms (61%) | 548 ms (**97.8%**) |
| 강제정렬 (Viterbi) | 9.8 ms (35%) | 11.2 ms (2.0%) |
| 진단·특징 | 1.2 ms (4%) | 1.4 ms (0.2%) |

**CPU 에서는 인코더가 전부다.** 최적화한다면 여기 말고 볼 곳이 없다.

**GPU 에서는 병목이 옮겨간다.** 12초 발화에서 정렬 20.5 ms > 인코더 18.6 ms 로 역전된다.
Viterbi 가 순수 numpy 단일 스레드고 음소 길이의 제곱에 가깝게 늘기 때문이다.
GPU 로 계속 간다면 여기가 다음 최적화 지점이다.

인코더는 발화 길이에 선형(6초 548 → 12초 961 ms), 정렬은 초선형이다.

## ③ 동시 요청 한계

서버는 `S["lock"]` 으로 인코더 호출을 **직렬화**한다(단일 GPU 전제). 따라서
워커 1개의 처리량 상한은 `1 / 지연` 이다.

6초 발화 기준:

| 구성 | 워커당 지연 | 워커 수 | **총 처리량** |
|---|--:|--:|--:|
| GPU 1장 | 28 ms | 1 | **35 req/s** |
| CPU 16스레드 × 1워커 | 561 ms | 1 | 1.8 req/s |
| CPU 4스레드 × 4워커 | 1,259 ms | 4 | **3.2 req/s** |
| CPU 8스레드 × 2워커 | 632 ms | 2 | 3.2 req/s |

**처리량을 원하면 스레드를 늘리지 말고 워커를 늘려야 한다.** 16스레드 1워커(1.8 req/s)보다
4스레드 4워커(3.2 req/s)가 1.8배 낫다. 대신 개별 응답은 561 ms → 1,259 ms 로 느려진다.

**메모리가 워커 수를 제한한다.** 워커 1개가 **RSS 5.17 GB** 를 쓴다(모델 파일은 1.18 GB
지만 fairseq 적재 오버헤드가 붙는다). 4워커 = 약 21 GB. 16 GB 머신이면 2워커가 상한이다.

모델 적재는 GPU 7.2초 / CPU 7.6초. 요청마다 올리면 안 되고 프로세스에 상주시켜야 한다.

## ④ 판단

**GPU 없이도 서비스는 된다.**

- 6초 발화에 **0.56초**(16스레드). 사용자가 말하고 결과를 받는 흐름에서 체감 지연으로 문제없다.
- 레슨 30문장 일괄 채점은 CPU 16.8초 / GPU 0.85초. 일괄 처리를 쓴다면 GPU 가 유리하다.
- 실시간 배수 10.7배라 스트리밍도 여유가 있다.

**단, 동시 사용자는 CPU 1대당 2~3명이 상한이다.** 그 이상은 큐가 쌓인다.
동시 접속이 늘면 CPU 인스턴스를 옆으로 늘리는 편이 GPU 1장보다 싸다 — GPU 1장이
35 req/s 인데 그만한 CPU 부하가 실제로 오는 서비스가 아니라면 GPU 는 과잉이다.

**8월 7일 이후 대응** — 코드 변경 없이 `--device cpu` 로 돌아간다.
`forward_lprobs` 의 `.half().cuda()` 만 CPU 분기를 타게 고치면 된다(이 스크립트의
`forward_cpu` 가 등가 구현이다).
