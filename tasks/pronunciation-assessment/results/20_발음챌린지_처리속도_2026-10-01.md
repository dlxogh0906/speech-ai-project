# 발음 챌린지 CTC 전환 — 처리속도·병목 점검 (2026-10-01)

> 질문: accent.beavertalk.im 의 발음 챌린지(30초 라운드, 약 2초마다 단어 1개, 즉시 PERFECT/MISS 판정)를
> 지금의 CTC 발음평가 모델로 바꿔도 화면 속도를 맞출 수 있나?
> 대상 모델: 발음평가 API(8932)가 쓰는 w2v-BERT 2.0 CTC `step_38000`.
> **API 코드는 고치지 않았고 8932 도 재시작하지 않았다** — 같은 코드를 별도 포트(8942)에 띄워 쟀다.

## 결론

1. **속도는 충분하다.** GPU 서버에서 단어 1개 판정이 **50~140 ms**(서버 처리 기준) — 단어 간격 2초의 3~7%.
   모델 계산보다 **"말이 끝났다"를 감지하는 대기 시간(보통 0.3~0.5초)** 이 체감 지연을 좌우한다.
2. **지금 API 를 그대로 붙이면 안 된다.**
   - 짧은 단어 발화의 **92.5% 가 "음성 부족"으로 거절**된다(입력 검사 기준이 문장용: 유성 구간 1.0초 이상).
   - 처리 시간의 60% 가 문장 점수용 회귀기(GBM)인데, PERFECT/MISS 판정에는 필요 없다.
   → **단어 모드 엔드포인트**가 따로 필요하다(§5).
   **둘 다 기준값·호출 생략만으로 풀리는 문제다(모델 재학습 불필요).** 데모(`mdd.word_judge`)에서 해결 확인(10-02):
   입력 기준 0.12초로 단어 거절 0.75% 이하 · 한 글자 단어(귀·키·입) 거절 0.2%, GBM 없이 서버 처리 약 45 ms.
3. **진짜 위험은 속도가 아니라 정확도다.** 맞게 읽었는데 MISS 가 뜨는 비율이
   **학습에 있던 단어 2~12%, 처음 보는 단어 22~69%**(판정 규칙에 따라). 챌린지 단어 목록이
   학습 단어 범위 안인지 먼저 확인해야 한다(§4).

## 1. 측정 조건

- 서버: A100-SXM4-80GB 1장, vCPU 16(EPYC 7H12). 측정 중 다른 GPU 작업 없음(단독 실행).
- 오디오: 16 kHz WAV, 실제 외국인 발화(AIHub)를 0.6~8초로 잘라 사용. 길이별 20~30회 중앙값.
- 서버 처리 시간만 잼 — **사용자↔서버 네트워크 왕복과 말끝 감지 대기는 포함 안 됨.**
- 스크립트: `scripts/eval/bench_pronunciation_latency.py`(단계별), `scripts/eval/load_test_pronunciation_api.py`(동시 요청).
  원본 JSON: `$MDD_OUTPUTS/analysis/latency_2026-10-01/`.

## 2. 단계별 처리 시간 (GPU, 한 요청)

| 오디오 길이 | 모델 forward | 문장 점수(GBM) | 나머지 | **합계** | p95 |
|---|--:|--:|--:|--:|--:|
| 0.6초 | 44 ms | 85 ms | 2 ms | **131 ms** | 143 ms |
| 1.0초 | 49 | 85 | 4 | **138** | 170 |
| 2.0초 | 53 | 83 | 6 | **142** | 195 |
| 5.0초 | 48 | 73 | 13 | **134** | 156 |

- 모델 forward 는 길이와 거의 무관(36~58 ms). 짧은 단어든 문장이든 비슷하다.
- **스레드 설정 하나로 2.5배 빨라진다.** 기본 설정에선 torch 와 GBM 이 CPU 스레드를 서로 뺏는다.
  `OMP_NUM_THREADS=4` 로 띄우면 GBM 85 → 13 ms, 합계 **52~65 ms**.
- 오디오 형식: 브라우저 기본 녹음(webm/opus)을 보내면 서버의 ffmpeg 변환이 **+119 ms**.
  16 kHz PCM/WAV 로 보내면 0.1 ms. (사이트는 이미 AudioWorklet 으로 16 kHz PCM 을 만들고 있다 — 그대로 보내면 된다.)
- GPU 메모리 1.25 GB/프로세스 — 한 GPU 에 여러 워커를 띄울 수 있다.

## 3. 동시 사용자

지금 API 서버는 요청을 **한 번에 하나씩** 처리한다. 2.56초 문장 클립으로 동시 요청을 걸었을 때:

| 동시 요청 | 기본 설정 p50 | `OMP_NUM_THREADS=4` p50 |
|--:|--:|--:|
| 1 | 133 ms | 66 ms |
| 4 | 529 ms | 261 ms |
| 8 | 1,164 ms | 507 ms |
| 16 | 2,296 ms | 1,012 ms |
| 처리량 | **약 7 요청/초** | **약 15.7 요청/초** |

챌린지 한 명이 2초에 단어 1개 → **0.5 요청/초/인**. 줄 서기 없이 받을 수 있는 동시 플레이어 수(프로세스 1개):

| 구성 | 처리량 | 동시 플레이어 | 근거 |
|---|--:|--:|---|
| 지금 API 그대로 | 7/초 | 약 14명 | 실측 |
| + `OMP_NUM_THREADS=4` | 15.7/초 | 약 30명 | 실측 |
| 단어 모드(GBM 생략) | 23~24.5/초 | 약 46명 | 실측(10-03, `deploy/pronunciation-challenge` · GPU · 동시 1~16) — results/21 §4-3 |
| + GPU 배치(16개 묶음) | 약 115~135/초 | 약 230명 이상 | **추정** — 배치 forward 실측(2초×16개 117~138 ms)만 반영 |

워커를 여러 개 띄우면 거의 선형으로 늘어난다(GPU 메모리 여유 충분). 동시 플레이어가 수십 명 이하면 배치까지 갈 필요는 없다.

**CPU 만 쓰는 경우**(GPU 없는 서버): 2초 이하 단어 **0.35~0.45 초**, 5초 문장 0.7~1.4 초.
단어 1개씩이면 화면에 쓸 수는 있지만 체감 지연이 커지고, 동시 플레이어는 프로세스당 한두 명 수준이다.

## 4. 정확도 — 맞게 읽어도 MISS 가 뜨는 비율

평가 데이터의 **단어 읽기 발화**로 셌다. "맞게 읽음" = 사람이 들은 실제 발음(TAG)이 표준발음과 같은 발화.

| 모델 / 단어 | 엄격 판정(자모 1개라도 다르면 MISS) | 느슨 판정(2개 이상 다르면 MISS) |
|---|---|---|
| 서비스 모델 · **학습에 있던 단어** (135종) | 억울한 MISS **12.0%** · 틀린 발음 잡음 68.4% | 억울한 MISS **2.2%** · 잡음 16.0% |
| 단어를 빼고 학습한 모델 · **처음 보는 단어** (10종) | 억울한 MISS **69.0%** · 잡음 89.5% | 억울한 MISS **22.0%** · 잡음 54.3% |

- 처음 보는 단어 쪽은 단어가 10종뿐이라 대략적인 값이다. 그래도 방향은 분명하다 — 이 모델은
  학습에 쓴 문장·단어를 외우는 경향이 있어서(`19_Stage2_MDD_인코더개선.md`), **처음 보는 단어에서는 헛지적이 크게 는다.**
- 학습에 있던 단어라도 엄격 판정이면 정확히 읽은 사람 8명 중 1명꼴로 MISS 가 뜬다. 게임이라면 느슨 판정이나
  "목표 음소만 본다" 같은 규칙이 필요하다. 다만 느슨할수록 틀린 발음을 놓친다(위 표의 "잡음").
- **할 일**: 챌린지 단어 목록을 받아 학습 단어와 겹치는지 확인 → 안 겹치는 단어는 빼거나 교체하는 것이 가장 싸다.

## 5. 구현 권장안

**클라이언트**
- 단어별로 오디오를 끊어서 보낸다. 방법은 두 가지:
  ① 단어가 뜬 시점부터 고정 구간(예: 2초 슬롯)을 잘라 보냄 — 구현이 가장 쉽고 지연은 슬롯 끝까지 기다리는 만큼.
  ② 말끝 감지(무음 0.3~0.5초) 후 즉시 보냄 — 반응이 빠르지만 VAD 튜닝 필요.
- 형식은 **16 kHz mono PCM/WAV** (webm 을 보내면 +119 ms).

**서버 (새 엔드포인트 — 지금 API 와 분리)**
- 입력: 오디오 + 목표 단어 → 출력: PERFECT/MISS + 틀린 자모 위치.
- 처리: 모델 forward + 정렬만. **문장 점수 GBM·유창성 계산은 생략.**
- 입력 검사 기준을 단어용으로 낮춘다 — 지금은 유성 1.0초 이상인데 단어 발화의 유성 구간 중앙값은 0.63초다.
  (10-02 재측정, 시험셋 단어 2,000개: API 기준 거절 95.2% → 0.2초 기준 0.75%. 단 한 글자 단어는 0.2초에서도 7.4% 가
  거절돼 데모는 **0.12초**로 둔다 — 한 글자 단어 거절 0.2%.)
- `OMP_NUM_THREADS=4`(또는 비슷한 값)로 프로세스를 띄운다.
- 동시 플레이어가 수십 명을 넘으면 워커 수를 늘리고, 수백 명이면 GPU 배치를 넣는다.

**데모**: 위 구성(브라우저 말끝 감지 + 16 kHz WAV + 단어 판정만)을 그대로 만든 것이 `deploy/pronunciation-challenge/`.
판정 로직은 라이브러리 `mdd.word_judge` 에 있어 서비스 엔드포인트에 그대로 가져다 쓸 수 있다.
단어 세트(학습 단어 · 처음 보는 단어)와 장치(GPU · CPU)를 페이지에서 바꿔 §3·§4 를 직접 체감할 수 있다.

## 6. 하지 않은 것

- 8932 API 코드 수정·재시작 없음. 입력 검사 기준·스레드 설정도 바꾸지 않았다(위는 권장 사항일 뿐).
- 네트워크 왕복, 브라우저 쪽 말끝 감지 시간, NPU(RBLN) 경로는 재지 않았다.
- GPU 묶음 처리(§3 표 마지막 줄)는 추정 그대로다. 단어 모드 처리량은 10-03 에 실측해 표를 고쳤다(results/21).
- 실제 챌린지 단어 목록으로 정확도를 재지 않았다 — 목록을 받으면 §4 를 그 단어로 다시 잴 수 있다.
