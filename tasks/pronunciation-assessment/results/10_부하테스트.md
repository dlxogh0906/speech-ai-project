# 10 — 부하 테스트 (2026-08-06)

`09_추론속도.md` 는 1건 지연을 쟀다. 이건 **동시에 던졌을 때 무엇이 먼저 무너지는가**와
**배치로 얼마나 더 뽑을 수 있는가**를 본다. GPU 종료(8/7) 전에 확보.

배포 모델 `mdd_ckpt_tag_all_native`. 장비 A100 80GB ×1 · CPU 16코어.

---

## ① 동시 요청 — 처리량은 안 오르고 대기만 쌓인다

살아 있는 API(`/diagnose_sample`, 10.2초 발화)에 동시 요청. 총 64건씩.

**GPU**

| 동시 | p50 ms | p95 ms | 최대 ms | 초당 건수 | 실패 |
|--:|--:|--:|--:|--:|--:|
| 1 | 43.8 | 44.9 | 355.3 | 20.4 | 0 |
| 2 | 84.2 | 89.5 | 115.4 | **23.4** | 0 |
| 4 | 169.4 | 191.6 | 227.7 | 23.1 | 0 |
| 8 | 349.8 | 431.7 | 443.4 | 22.3 | 0 |
| 16 | 678.6 | 876.8 | 883.0 | 21.7 | 0 |
| 32 | 1,434 | 1,691 | 1,755 | 20.8 | 0 |
| 64 | 1,948 | 3,236 | 3,360 | 18.9 | 0 |

**CPU** (`MDD_FORCE_CPU=1`, 총 16건씩)

| 동시 | p50 ms | p95 ms | 초당 건수 | 실패 |
|--:|--:|--:|--:|--:|
| 1 | 935 | 985 | 1.08 | 0 |
| 2 | 1,874 | 2,316 | 1.04 | 0 |
| 4 | 3,797 | 4,130 | 1.04 | 0 |
| 8 | 7,851 | 8,787 | 0.99 | 0 |
| 16 | 8,885 | 15,663 | 1.02 | 0 |

**처리량은 동시성과 무관하게 평평하다** — GPU 약 21건/초, CPU 약 1건/초.
서버가 `S["lock"]` 으로 인코더를 직렬화하기 때문이다. 동시 요청을 늘리면 대기만 선형으로
쌓인다(GPU 동시 64 → p95 3.2초, CPU 동시 16 → p95 15.7초).

**실패는 0건이다.** 타임아웃·메모리·커넥션 어디도 안 터졌다. 동시 64까지는 느려질 뿐
깨지지 않는다. 즉 **부하 대응은 "안정성"이 아니라 "지연"의 문제다.**

**64/128 을 굳이 더 잴 필요가 없다.** 이 구조에서는 `지연 ≈ 동시수 ÷ 처리량` 으로
예측되고, 실측이 그 예측과 일치한다(GPU 동시 64 → 64/21 = 3.0초 vs 실측 p95 3.2초).

## ② 배치 — 여기에 4.6배가 남아 있다

`forward_lprobs` 는 원래 여러 발화를 한 번에 받는다. **지금 서버가 1건씩 부를 뿐이다.**
6초 발화 동일 길이 기준, 인코더 forward 만:

| 배치 | 배치 전체 ms | 발화당 ms | 초당 건수 | GPU 메모리 |
|--:|--:|--:|--:|--:|
| 1 | 17.0 | 17.0 | 58.7 | 0.74 GB |
| 2 | 19.5 | 9.8 | 102.5 | 0.87 GB |
| 4 | 22.6 | 5.6 | 177.2 | 1.13 GB |
| **8** | **33.5** | **4.2** | **238.6** | 1.64 GB |
| 16 | 63.0 | 3.9 | 253.8 | 2.67 GB |
| 32 | 120.5 | 3.8 | 265.6 | 4.73 GB |
| 64 | 235.5 | 3.7 | 271.7 | 8.84 GB |
| 128 | 469.6 | 3.7 | 272.6 | 17.07 GB |

**배치 8에서 이미 포화한다.** 8→128 로 16배 키워도 처리량은 238 → 273 (+14%)뿐인데
사용자 대기는 33 ms → 470 ms 로 14배 나빠진다.

메모리는 제약이 아니다 — 배치 128 이 17 GB 로 80 GB 중 21%다. **연산이 먼저 포화한다.**

### 배치를 넣으면 실제로 얼마가 되나

인코더는 58.7 → 238 건/초(4.1배)로 오르지만, **강제정렬(Viterbi)은 배치가 안 된다.**
순수 numpy 단일 스레드로 발화당 9.8 ms 라 한 스레드에서 102 건/초가 상한이다.

따라서 배치만 넣으면 병목이 인코더에서 정렬로 옮겨간다. 정렬을 스레드 풀로 돌려야
인코더 상한(238)에 닿는다. 현재 21 건/초에서 **약 10배**가 현실적 목표다.

## ③ CPU 전환 — 코드가 GPU 없이는 죽고 있었다

`Decoder.__init__` 이 `.cuda().half()` 를, `forward_lprobs` 가 `.half().cuda()` 를 무조건
걸고 있었다. **8월 7일 GPU 종료 시점에 API 가 적재 단계에서 죽는다.**

장치를 모델 파라미터에서 읽도록 고쳤다. GPU 가 있으면 fp16 GPU, 없으면 fp32 CPU.
`MDD_FORCE_CPU=1` 로 강제 전환할 수 있다.

**GPU 경로 수치는 그대로다.** 같은 샘플을 GPU(8914)와 CPU(8916)에 각각 태워 대조했다:

| 샘플 | GPU 인식 | CPU 인식 | 지적 | 미인식 | 일치율 |
|---|---|---|--:|--:|--:|
| 5 | `ㅋㅡㅊㅣ` | `ㅋㅡㅊㅣ` | 1 / 1 | 0 / 0 | 0.75 / 0.75 |
| 7 | `ㄴㅏㅅㅣㅎㅓㅁ…ㅂㅉㅣ` | 동일 | 0 / 0 | 4 / 4 | 1.0 / 1.0 |

## ④ 판단

**동시 사용자 기준선** (p95 3초 이내를 허용선으로 볼 때)

| | 처리량 | 허용 동시 사용자 |
|---|--:|--:|
| GPU 1장 (현재) | 21 건/초 | **약 60명** |
| GPU 1장 + 배치 | 약 200 건/초 (추정) | 수백 명 |
| CPU 16코어 1워커 | 1 건/초 | **2~3명** |

**지금 구조로도 GPU 1장이면 동시 60명까지 버틴다.** 배치는 그보다 훨씬 커진 뒤에
필요한 최적화다 — 지금 넣을 이유가 없다.

**CPU 로 내려가면 동시 2~3명이 상한이다.** 그 이상은 인스턴스를 옆으로 늘려야 한다.
CPU 인스턴스 7대가 GPU 1장과 맞먹는다.
