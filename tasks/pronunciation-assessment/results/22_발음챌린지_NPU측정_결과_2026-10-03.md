## 0. 한 줄 결론

- **판정은 GPU 와 완전히 같다** — 등급 24/24 · 들린 자모열 24/24 (OMP 4 · 기본 모두).
- **단어 판정 서버 처리 30~50 ms** → 목표 100 ms 이하 충족. 프로세스 1개 ≈ **20 건/초(동시 플레이어 약 40명)**, 장치를 하나 더 쓰면 **2배로 늘어난다**(19.2 + 19.2 건/초).
- **스레드 수가 NPU 호출 시간을 좌우한다** — `OMP_NUM_THREADS` 1→67 ms · 4→42 · **8~16→28** · 32→130. 운영 `start_pron.sh` 의 `OMP_NUM_THREADS=4` 는 이 서버에서 최적이 아니다(8 이 좋다). GPU 서버 결론(4 가 최적)은 NPU 서버에 그대로 적용되지 않는다.
- 운영 API 경로의 점수 단계(numpy 트리)는 1.5~3 ms 로 GPU 서버 GBM(13.8 ms)보다 훨씬 싸다 — NPU 서버에서는 "GBM 이 60%" 문제가 없다. 단어 전용 경로의 이득은 입력 검사 완화와 저장 생략이지 속도가 아니다.

## 3. 새로 알게 된 것 — 스레드 수가 NPU 호출 시간을 바꾼다

`RBLNDecoder.lprobs` 를 분해(`probe_fwd.py`, 반복 15 중앙값, 장치 6번, 두 번 돌려 재현 확인):

| `OMP_NUM_THREADS` | 특징 추출 (단어 1.68초) | **NPU 호출** `rt.run` (192 버킷) | NPU 호출 (448 버킷, 5.5초) |
|--:|--:|--:|--:|
| 1 | 2.1~3.6 ms | 49~67 ms | 207 ms |
| 4 (운영 설정) | 5.5 ms | **42 ms** | 126 ms |
| **8** | 2.7~3.3 ms | **29 ms** | 98~117 ms |
| 16 | 5.3 ms | **28 ms** | 79 ms |
| 32 (= nproc) | 2.1 ms | 130 ms | 152~172 ms |

- `rt.run()` 은 numpy 입력을 받는 순수 런타임 호출인데도 OMP 스레드 수에 따라 2~4배 차이가 난다 → rebel 런타임이 호스트 쪽 전·후처리(입출력 복사·레이아웃 변환으로 추정)에 OpenMP 스레드 풀을 쓴다.
- 32(코어 수 전부)는 국적 서비스 17+9 프로세스와 코어를 다퉈 오히려 가장 느리다. **8 이 안전한 최적**(16 과 같고, 다른 서비스에 덜 끼친다).
- 후처리(log_softmax)는 0.1 ms 미만. 특징 추출은 2~10 ms 로 스레드 수와 무관하게 흔들린다.
- **운영 API(`start_pron.sh`)는 `OMP_NUM_THREADS=4` 로 떠 있다.** 8 로 바꾸면 단어·짧은 문장 forward 가 42 → 29 ms 로 줄 것으로 보인다. 이번에는 운영을 건드리지 않았다 — 바꾸려면 재시작이 필요하니 사용자 판단.
- 파일: `npu_probe_threads.txt`.

## 4. 네트워크 — 요청서(10-03 웹 담당) §5-2 4번 항목

NPU 서버 안에서 본 것(`tailscale status` · `funnel status` · `netcheck` · `ping`, 20:21 KST):

| 항목 | 값 |
|---|---|
| Funnel | 켜짐. `:443` → `127.0.0.1:8905`(국적) · `:8443` → `<NPU-tailscale-IP>:8932`(발음) |
| 가장 가까운 DERP | **홍콩(hkg)** (서울 DERP 없음) |
| NPU 공인 IP | <NPU-공인-IP> (UDP 가능, 포트매핑 없음) |
| 피어 `lyg`(윈도우 PC) | **직접 연결** 21 ms |
| 피어 `nationality-gpu`(GPU 서버) | **DERP(hkg) 중계** 78 ms · "direct connection not established" |

- GPU 서버 ↔ NPU 서버 왕복 581 ms(21번 §1-11)의 원인은 **중계 경로**다. 직접 연결이 안 맺힌다(GPU 서버 쪽 NAT·방화벽 문제로 추정, NPU 쪽은 UDP 열려 있음).
- 웹 서버(Cloud Run 서울) → Funnel → NPU 경로는 Tailscale 구조상 **항상 Tailscale 의 Funnel 입구를 거쳐 중계**된다(Funnel 은 직접 연결이 없다). 입구가 도쿄·홍콩이면 서울 ↔ 도쿄/홍콩 ↔ 서울 왕복이 기본으로 붙는다. 첫 연결 3.9초는 그 위에 TLS 핸드셰이크 + 입구 쪽 연결 수립이 겹친 값으로 보이며, 서버 안에서는 더 좁힐 수 없다.
- 줄이는 길은 요청서 대안 C(웹 서버를 테일넷에 붙여 직접 연결)뿐이다. 다만 Cloud Run ↔ NPU 가 직접 연결(UDP 홀펀칭)을 맺을 수 있어야 하고, 안 되면 또 DERP 다. 붙인 뒤 `tailscale ping` 으로 확인해야 한다.

## 6. 권고

1. **단어 판정 경로를 운영 API(8932, Funnel `:8443`)에 붙인다** — 새 경로 `POST /word.judge` 또는 `/sent.eval.kr?mode=word`. 로직은 `mdd.word_judge.WordJudge.judge()` 그대로(입력 검사 0.12초 · GBM 생략 · 저장 안 함). 응답은 요청서 §5-1 형식(`canon_jamo` · `pred_jamo` · `mismatches` · `n_mismatch` · `voiced_sec` · `ms`) — `judge()` 의 `canon`·`pred`·`sites`·`edit` 를 그대로 이름만 맞추면 된다. 같은 프로세스에서 같은 런타임을 쓰므로 메모리 추가 없음.
2. **운영 프로세스의 `OMP_NUM_THREADS` 를 4 → 8 로** (재시작 필요, 사용자 판단). 단어 forward 42 → 29 ms.
3. 동시 플레이어가 40명을 넘기면 7번 외 장치에 프로세스를 하나 더 띄우고 앞단에서 나눈다(3버킷은 장당 1개). 더 촘촘히 올리려면 192 버킷 단독 컴파일(약 3분)을 따로 검증.
4. 네트워크는 서버 쪽에서 할 것이 없다. 웹 쪽 대안 C 를 시도하면 `tailscale ping` 으로 직접 연결 여부를 확인해 달라.
