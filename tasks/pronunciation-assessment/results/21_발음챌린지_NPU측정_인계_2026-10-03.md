# 21 — 발음 챌린지 처리속도: NPU 서버 측정 인계 (2026-10-03)

> **읽는 사람: NPU 서버(`<NPU-tailscale-IP>`, `/root/pron_serve`)에서 작업하는 Claude.**
> `results/20`(GPU 서버 측정)에서 찾은 문제와 해결 방법을 정리하고, 같은 항목을 NPU 서버에서 재는 절차를 적었다.
> **같은 측정 묶음(발화 24개)으로 GPU 서버 기준값을 이미 재 두었다**(§4) — NPU 값만 채우면 바로 비교된다.
> 배경: 웹사이트 발음 챌린지(30초 라운드 · 약 2초에 단어 하나 · 즉시 PERFECT/MISS)를 CTC 모델로 바꿀 수 있는지.

## 0. NPU 서버에서 지킬 것

- **운영 발음 API(8932, NPU 7번, `start_pron.sh`)를 건드리지 않는다.** 재시작·설정 변경 금지. 측정은 별도 프로세스 · 별도 포트.
- **`/root/pron_serve/app` 안에 파일을 넣지 않는다** — 운영이 읽는 폴더다. 복사본(`/root/pron_bench/app`)을 만들어 거기서 돌린다(§3-1).
- 국적 서비스(8905 · 8906, NPU 0~7번)를 건드리지 않는다. 이미 쓰는 포트를 쓰지 않는다(`ss -ltn` 으로 확인).
- **`tailscale serve` 금지**(funnel 이 꺼진다). 측정은 localhost 에서만 한다. 외부 공개가 필요하면 사용자에게 먼저 묻는다.
- 토큰 파일(`/root/pron_serve/.token`) 내용을 출력하지 않는다.
- **NPU 메모리**: 7번은 11.4 / 15.7 GiB 라 3버킷 인스턴스(5.0 GiB)가 더 안 들어간다. 0~6번 중 하나(각 6.4 GiB 사용 중)에 올린다
  → 11.4 GiB. 그 장은 국적 서비스와 같이 쓰므로 `rbln-stat` 으로 한가한 장 · 한가한 시간을 고르고, 측정 중에 국적 응답이 느려지지 않는지 본다.
- 속도 측정은 하나씩 단독으로 돌린다(동시에 돌리면 값이 부풀려진다).
- 측정 묶음에는 AIHub 발화가 들어 있다 — 서버 밖으로 내보내지 않고, 끝나면 지워도 된다.

## 1. results/20 에서 찾은 문제와 해결 방법

GPU 서버(A100)에서 운영 발음 API 코드(`deploy/pronunciation-demo/app.py`)를 그대로 재서 찾았다.
1~4번은 **단어 전용 판정 모듈 `mdd.word_judge` + 챌린지 서버 `deploy/pronunciation-challenge`** 로 풀었다(운영 API 는 그대로).

| # | 문제 (GPU 실측) | 원인 | 해결 방법 | NPU 에서 할 일 |
|---|---|---|---|---|
| 1 | **짧은 단어가 "음성 부족"으로 거절** — 단어 95.2%, 한 글자 단어 97.5% | API 입력 검사 `check_audio()` 가 문장용: 유성 구간 `MIN_VOICED_SEC = 1.0`초 · 비율 `MIN_VOICED_RATIO = 0.30`. 단어 발화 유성 구간 중앙값 0.63초, 한 글자 0.39초 | `mdd.word_judge.MIN_VOICED_SEC = 0.12`(비율 조건 없음). 0.2초로도 한 글자 단어 7.4% 가 거절돼 0.12초로 내림 → 단어 거절 0.75% 이하 · 한 글자 0.2%. 미달이면 MISS 가 아니라 `NO_SPEECH`(다시 말하기) | **없음** — 장치와 무관한 값이다 |
| 2 | **처리 시간의 60% 가 게임에 필요 없는 문장 점수(GBM)** — 요청당 70~85 ms | `analyze()` 가 매 요청 `SessionScorer.utt_scores`(GBM 회귀기)·유창성·L1 피드백까지 돈다 | `WordJudge.judge()` 는 무음 다듬기 → 모델 → 그리디 자모열 → 표준발음과 편집거리(edlib)만. 0 PERFECT · 1 GOOD · 2 이상 MISS | NPU 서버 API 는 sklearn 대신 numpy 트리(`mdd.hgbr_np`)로 점수를 낸다 → **점수 단계가 GPU 서버와 다를 수 있다.** §3-3 으로 단계별로 잰다 |

| 5 | **요청을 한 번에 하나씩 처리** — 운영 API 프로세스 1개 7 건/초(동시 약 14명), 3번 적용 후 15.7 건/초(약 30명). 단어 판정 서버는 23~24 건/초(약 46명, 10-03 실측) | 서버가 동기 처리. 한 명이 2초에 단어 1개 = 0.5 건/초 | 동시 인원이 늘면 프로세스(워커)를 늘린다. | 8 | **정확도: 맞게 읽어도 MISS** — 학습한 단어 2.2%, 처음 보는 단어 22% (자모 1개라도 다르면 MISS 로 치면 12% / 69%) | 모델이 학습 문항을 외운다(results/19) | **로직으로는 못 고친다.** 챌린지 단어를 학습 범위에서 고르거나 데이터로 풀어야 한다 | NPU 가 GPU 와 **같은 판정을 내는지만** 확인한다(§3-2 `--ref`) |

`mdd.jamo_to_kog2p` · `shared.paths`(KoG2P) · `edlib`. 운영 API 가 쓰는 것들이라 번들에 있다. **import 에러가 나면 번들 쪽 그 파일이 오래된 것** —
GPU 서버 저장소의 같은 파일을 복사본에만 덮는다. GPU 서버에서는 NPU 가 없어 `npu` 경로를 **실행해 보지 못했다** — 처음 돌릴 때 고칠 곳이 나올 수 있다.

## 3. 측정 절차 (NPU 서버)

### 3-1. 준비

```bash
mkdir -p /root/pron_bench && cp -a /root/pron_serve/app /root/pron_bench/app      # 운영 폴더는 그대로 둔다
cp -a /root/pron_bench/pack/code/. /root/pron_bench/app/                           # 새 코드는 복사본에만
cd /root/pron_bench/app
PY=/root/nat_serve/venv/bin/python                                                 # Python 3.12 · rebel 0.10.2
PK=/root/pron_bench/pack
RBLN=/root/pron_serve/w2vbert_ctc_f192_448_1024.rbln
cat /root/pron_serve/start_pron.sh        # --hf-ckpt(model_fp32/) · --scorer(npz) · --norms 등 실제 인자를 여기서 확인해 아래에 그대로 쓴다
rbln-stat                                  # 한가한 장 번호 → DEV (7번 제외)
```

### 3-2. 단어 판정 속도 + GPU 와 판정 일치 (핵심)

```bash
OMP_NUM_THREADS=4 $PY tasks/pronunciation-assessment/scripts/eval/judge_pack.py --pack $PK \
    --hf-ckpt <start_pron.sh 의 --hf-ckpt> --device npu --rbln $RBLN --rbln-device $DEV \
    --ref $PK/ref_cuda.jsonl --out $PK/npu_judge_omp4.jsonl
$PY tasks/pronunciation-assessment/scripts/eval/judge_pack.py ... --out $PK/npu_judge_default.jsonl      # OMP 기본값
```

출력: 단어 · 긴 발화별 모델 ms · 판정 전체 ms(중앙값), GPU 와 등급 · 자모열 일치 수, 등급이 다른 발화 목록.

### 3-3. 운영 API 경로 단계별 (점수 단계가 GPU 서버와 다른지)

```bash
OMP_NUM_THREADS=4 $PY tasks/pronunciation-assessment/scripts/eval/bench_pronunciation_latency.py --clips-dir $PK \
    --hf-ckpt <...> --scorer <start_pron.sh 의 --scorer> --score-dir <norms.json · calibration.json 등이 있는 폴더> \
    --rbln $RBLN --rbln-device $DEV --durations 0.6 1.0 2.0 3.0 5.0 8.0 --out $PK/npu_bench_omp4.json
# OMP 기본값으로 한 번 더 → npu_bench_default.json
```

단계: decode · check · trim · canonical · **forward(NPU)** · feats · align · l1 · **score(GBM)** · build · total.
`--score-dir` 의 파일 이름이 다르면(`norms.json` · `calibration.json` · `fluency_rule.json` · `utt_percentile.json`) start_pron.sh 의 인자를 보고 맞춘다.
없는 파일은 앱이 기본값으로 물러난다.

### 3-4. 챌린지 서버 + 동시 요청

```bash
ss -ltn                                     # 빈 포트 확인 → PORT (8932 · 8905 · 8906 등 쓰는 포트 금지)
OMP_NUM_THREADS=4 $PY deploy/pronunciation-challenge/app.py --hf-ckpt <...> --devices npu \
    --rbln $RBLN --rbln-device $DEV --prompts-json $PK/train_prompts.json --port $PORT     # tmux 안에서
$PY tasks/pronunciation-assessment/scripts/eval/load_test_pronunciation_api.py --mode judge \
    --url http://127.0.0.1:$PORT/judge --device npu --wav $PK/word_2s.wav --text 소리 \
    --concurrency 1 4 8 16 --out $PK/npu_load_judge.json
```

동시 인원 ≈ 처리량(건/초) ÷ 0.5. 끝나면 서버를 내린다.

### 3-5. (선택) 프로세스 2개

다른 장(DEV2)에 서버를 하나 더 띄우고 두 포트에 부하를 나눠 걸면 처리량이 2배가 되는지 볼 수 있다. 장 메모리와 국적 서비스 영향을 먼저 확인한다.

### 3-6. 정리

측정 서버를 모두 내리고(`ss -ltn` 으로 포트 확인), 결과 JSON 만 남기고 `/root/pron_bench/pack/clips` 는 지워도 된다.

## 4. 결과 표 — GPU 기준값은 채워 둠, NPU 칸을 채울 것

(GPU 기준: A100-SXM4-80GB, vCPU 16, `OMP_NUM_THREADS=4`, 2026-10-03 GPU 유휴 상태에서 단독 측정. 같은 묶음.)

### 4-1. 단어 판정 (`judge_pack.py`, 중앙값)

| 장치 | 단어 12개 모델 | 단어 판정 전체 | 문장 12개 모델 | 문장 판정 전체 | GPU 와 등급 일치 | 자모열 일치 |
|---|--:|--:|--:|--:|--:|--:|
| GPU (fp16) | 36.7 ms | 37.2 ms | 52.7 ms | 53.7 ms | 기준 | 기준 |
| GPU 서버 CPU (fp32, 4스레드) | 569.5 ms | 570.0 ms | 2,430 ms | 2,431 ms | **24 / 24** | **24 / 24** |
| **NPU** (OMP 4) | | | | | / 24 | / 24 |
| **NPU** (OMP 기본) | | | | | | |

GPU ↔ CPU 일치 수가 "정밀도만 다른 같은 모델"의 기준선이다. NPU 일치가 이와 비슷하면 같은 판정으로 본다
(results/17_NPU: 실제 녹음 161건 중 자모열 157건 일치).

### 4-2. 운영 API 경로 단계별 (`bench_pronunciation_latency.py`, 중앙값 ms)

| 길이 | GPU forward | GPU score(GBM) | GPU 합계 | GPU p95 | NPU forward | NPU score | NPU 합계 | NPU p95 |
|---|--:|--:|--:|--:|--:|--:|--:|--:|
| 0.6초 | 35.8 | 13.8 | 52.7 | 60.8 | | | | |
| 1.0초 | 36.6 | 13.8 | 53.8 | 60.6 | | | | |
| 2.0초 | 38.5 | 13.9 | 56.8 | 64.5 | | | | |
| 3.0초 | 41.3 | 13.2 | 65.4 | 72.3 | | | | |
| 5.0초 | 47.0 | 13.0 | 73.2 | 87.3 | | | | |
| 8.0초 | 54.1 | 12.9 | 85.0 | 91.5 | | | | |

GPU 는 `OMP_NUM_THREADS=4` 값이다(기본 스레드면 score 가 70~85 ms 로 커진다 — results/20 §2).
GPU 묶음 처리(2초 × 16개 forward 119 ms, 개당 7.4 ms)는 NPU 런타임이 한 번에 하나라 해당하지 않는다.

### 4-3. 챌린지 서버 동시 요청 (`--mode judge`, "소리" 1.96초)

## 5. 서버 안에서 못 재는 것

- **사용자 → funnel → NPU 서버 왕복.** 서버 처리(수십 ms)보다 클 수 있다. 사용자 쪽(브라우저 · 휴대폰)에서 재야 한다.
  참고: GPU 서버 ↔ NPU 서버 tailnet 왕복은 581 ms 였다(Tailscale 중계).
- 휴대폰 마이크로 실제 게임을 해 보는 것(말끝 감지 체감).
- 챌린지 단어 목록으로 정확도 다시 재기 — 목록을 받아야 한다(§1-8).
