# 자리 단위 MDD 보정기 — correct / uncertain / incorrect

`17_MDD_오류분석` §12-A 의 1단계. 인코더(`w2vbert_stage2/step_38000`)는 그대로 두고, 이미 계산하는
신호(margin GOP · 자리 문맥 · 발화 특징)로 **자리마다 3상태를 판정하는 분류기**를 학습했다.

**서비스(8932 API)에는 연결하지 않았다.** 코드는 `mdd.mdd_calibrator`(라이브러리)와 학습 스크립트뿐이고,
번들도 API 가 읽는 `score_phoneme/` 이 아니라 `analysis/mdd_calibrator/` 에 있다.

작성 2026-09-27 · 개정 같은 날(검증 절차 분리 — 아래 "절차" 참고)

## 절차 — test 는 마지막에 한 번만

첫 버전은 임계값을 test 에서 골랐다. 그래서 학습·선택·최종 평가를 나눠 다시 했다
(`train_mdd_calibrator.py select` → `final`).

```
            w2v-BERT step_38000 고정 → margin GOP · 발화 특징
                                │
   manifest_tag_rebuilt / train 200,000발화 (화자 9,436)
          │ 화자 기준 80:20 (seed 42)
   ┌──────┴────────────────┐
calibrator_train          calibrator_valid                 manifest_tag_rebuilt / test
화자 7,549 · 160,346발화   화자 1,887 · 39,654발화          화자 1,196 · 178,049발화
모델 학습                 특징 묶음·임계값·재녹음 기준 선택   select 동안 열지 않음
                                │
                              잠금 (mdd_calibrator.joblib)
                                │
                                └──────────────→  final: 한 번 적용 (final_test.json)
```

- test 화자는 train 과 겹치지 않는다(매니페스트가 보장, 스크립트가 다시 확인).
- `final` 은 결과 파일이 이미 있으면 실행을 거부한다(`--force` 없이는 두 번 못 본다).
- 첫 버전 산출물은 `_v0_threshold_on_test/` 로 옮겨 두었다. 그 수치(정밀도 0.650)는 인용하지 말 것.

## 1. 특징 축소 실험 (valid 에서만)

리뷰 가설: "신호가 대부분 margin GOP 에 있으니 특징을 줄여도 비슷하지 않나?"

| 묶음 | 특징 | AUC | AP | 임계값 inc / unc | incorrect P | R | **F1** |
|---|--:|--:|--:|---|--:|--:|--:|
| full | 29 | 0.9469 | 0.5327 | 0.46 / 0.27 | 0.652 | 0.377 | **0.4775** |
| full_mism | 30 | 0.9475 | 0.5395 | 0.48 / 0.27 | 0.656 | 0.378 | 0.4796 |
| tiny (margin·전사불일치·자모·위치) | 4 | 0.9446 | 0.4983 | 0.51 / 0.26 | 0.652 | 0.289 | 0.4008 |
| minimal (margin·전사불일치) | 2 | 0.9428 | 0.4548 | 0.61 / 0.24 | 0.643 | 0.126 | 0.2103 |

**가설은 틀렸다 — 문맥 특징이 실제로 중요하다.** 같은 정밀도(≈0.65)에서 재현율이
0.377 → 0.289(4개) → 0.126(2개)로 무너진다. AUC 는 0.947 → 0.943 으로 거의 같아서
**AUC 만 보면 이 차이가 안 보인다** — 고정밀 구간에서만 벌어진다.
(앞선 순열 중요도에서 margin 이 압도적이었던 건 "순서 매기기"(AP) 기여였고,
높은 정밀도에서 얼마나 건지느냐는 발화·문맥 특징이 좌우한다.)

선택 규칙: valid F1 최고값에서 0.005 안이면 가장 작은 묶음 → full·full_mism 이 후보, **full(29) 채택**.

## 2. 최종 test (한 번)

| 판정 방식 | 지적 수 | 정밀도 | 재현율 | F1 | 억울한 지적(FP) |
|---|--:|--:|--:|--:|--:|
| 전사 불일치만 | 74,340 | 0.474 | 0.518 | 0.495 | 39,128 |
| 현재 서비스 규칙 (전사 불일치 AND 음소점수 < 60) | 38,970 | 0.557 | 0.319 | 0.406 | 17,269 |
| **보정기 incorrect** | 38,987 | **0.648** | **0.372** | **0.472** | **13,727** |

- valid 에서 예측한 값(P 0.652 · R 0.377)과 test 값(P 0.648 · R 0.372)이 거의 같다 — **일반화된다.**
- 첫 버전(test 에서 임계값 선택)의 0.650 / 0.369 와도 거의 같아, 그때 test 에 과적합된 건 아니었다.
- 지적 수를 맞춘 현재 서비스 규칙 대비 **정밀도 +9.1%p · 재현율 +5.2%p · 억울한 지적 −21%**.

3상태 분포(test):

| 상태 | 자리 비중 | 안쪽 진짜 오류율 | 진짜 오류 중 이 칸 |
|---|--:|--:|--:|
| incorrect | 2.18% | 64.8% | 37.2% |
| uncertain | 2.59% | 32.9% | 22.4% |
| correct | 95.23% | 1.61% | 40.4% (놓침) |

## 3. 오류 유형·위치·약한 쌍별 — 어디서 좋아졌고 어디선 아닌가 (test)

재현율(진짜 오류 중 지적한 비율):

| 구분 | 진짜 오류 | 전사만 | 서비스 규칙 | 보정기 |
|---|--:|--:|--:|--:|
| 대치 | 57,082 | 0.516 | 0.328 | **0.392** |
| 삭제 | 10,900 | 0.526 | **0.275** | 0.263 |
| 중성(모음) | 13,608 | 0.401 | 0.131 | **0.215** |
| 초성 | 39,868 | 0.518 | 0.356 | **0.392** |
| 종성 | 14,506 | 0.627 | 0.395 | **0.462** |
| ㅅ→ㅆ | 1,137 | 0.115 | 0.000 | 0.036 |
| ㅈ→ㅊ | 1,487 | 0.256 | 0.061 | 0.153 |
| ㄱ→ㅋ | 1,957 | 0.365 | 0.008 | 0.107 |
| ㄸ→ㄷ | 1,546 | 0.396 | 0.303 | 0.343 |
| ㅉ→ㅈ | 1,534 | 0.445 | 0.297 | 0.318 |
| ㄹ→ㄴ | 2,420 | 0.738 | 0.139 | **0.593** |
| ㄴ→ㄹ | 2,467 | 0.814 | 0.624 | 0.735 |
| ㅇ→ㄱ | 2,011 | 0.850 | 0.805 | 0.799 |

위치별 정밀도(그 위치에서 지적한 것 중 진짜 오류):

| 위치 | 전사만 | 서비스 규칙 | 보정기 |
|---|--:|--:|--:|
| **중성(모음)** | 0.334 | 0.365 | **0.570** |
| 초성 | 0.511 | 0.579 | 0.654 |
| 종성 | 0.517 | 0.598 | 0.673 |

읽는 법 — **좋아진 것과 안 된 것이 분명하다.**

- **모음은 지적의 정확도가 크게 올랐다**(정밀도 0.365 → 0.570). 모음 헛지적이 가장 많던 곳이라 체감이 클 것이다.
- **약한 쌍(ㅅ→ㅆ·ㅈ→ㅊ·ㄱ→ㅋ)은 사실상 그대로다.** 서비스 규칙보다는 낫지만 재현율 4~15% 다.
  원인은 구조적이다 — incorrect 는 "전사 불일치 AND" 라서 **전사가 애초에 못 잡은 오류는 보정기도
  못 잡는다**(ㅅ→ㅆ 은 전사 단계에서 이미 11.5% 뿐). 이 쌍은 인코더가 들어야 풀린다 → 재학습(P3) 대상.
- **삭제는 서비스 규칙보다 조금 나쁘다**(0.275 → 0.263).
- **삽입은 해당 없음** — 표준발음에 자리가 없어 자리 단위 보정기가 판정하지 않는다.
  삽입 개선도 인코더 쪽(재학습) 몫이다.

## 4. uncertain 의 뜻 — 서비스 문구 주의

uncertain 은 **"오류일 가능성이 중간인 자리"** 다(안쪽 실제 오류율 약 33%).
**"모델이 잘 못 들은 자리"로 검증된 것이 아니다** — margin 만으로는 학습자 오발음과 모델 인식 실수를
가를 수 없음이 측정됐다(`17` §10). 그래서 서비스에서는:

| 상태 | 문구 |
|---|---|
| incorrect | "ㅅ을 ㅆ처럼 발음했어요" (그 자리만) |
| uncertain | **그 자리에 대한 직접 지적을 하지 않는다** |
| 발화 전체에 uncertain 이 많음 | "발음을 정확히 확인하기 어려워요. 다시 한번 말해주세요." |
| 그 외 | 통과 |

"모델이 잘 못 들었어요" 같은 문구는 쓰지 않는다.

## 5. 재녹음 기준 — valid 에서 비교한 휴리스틱

uncertain 자리 비율이 기준 이상이면 재녹음 안내. 기준별(valid, full 묶음):

| 재녹음 기준 | 재녹음 전체 | 깨끗한 발화 재녹음 | 오류 발화 재녹음 | 깨끗한 발화 억울한 지적 | 깨끗한 발화 통과 |
|--:|--:|--:|--:|--:|--:|
| 20% | 7.07% | 5.38% | 11.94% | 6.74% | 87.9% |
| 25% | 4.25% | 3.31% | 6.93% | 6.97% | 89.7% |
| **30%** | **1.90%** | 1.45% | 3.18% | 7.08% | 91.5% |
| 40% | 0.79% | 0.56% | 1.47% | 7.13% | 92.3% |

- 재녹음은 오류를 잘 가려내지 못한다 — 기준 30%에서 깨끗한 발화 1.45% vs 오류 발화 3.18%(2.2배 차이뿐).
  **억울한 지적은 기준과 거의 무관하게 7% 안팎**이라, 재녹음을 늘려서 얻는 게 적다.
- 그래서 **재녹음은 최소로(30%)** 두고, 애매한 자리는 "지적하지 않음"으로 처리하는 쪽을 권한다.
  30% 는 최적값이 아니라 **재녹음 빈도를 2% 안팎으로 묶는 제품 선택**이다.
- test 결과(30%): 재녹음 2.05% · 깨끗한 발화 통과 91.4% · 깨끗한 발화 억울한 지적 7.05%.

## 6. 아직 측정하지 않은 것

- **안 본 문장에서의 보정기 성능(P2).** RP 평가셋(`17` §9)은 문단이라 중위 44초고, margin 추출도
  길이 문제를 그대로 받는다(20초 초과에서 출력 누락). 분할 디코드는 되지만 margin 추출
  (`gop_feats_v2`, 강제정렬)은 아직 분할을 지원하지 않는다. 문항 홀드아웃 재학습(P3 이후)으로
  깨끗한 조건을 만든 뒤 재는 것이 맞다.
- 쌍별 정밀도(예: ㅅ 자리에서 지적한 것 중 실제 ㅅ→ㅆ). 위치별 정밀도까지만 냈다.

## 7. 앞으로 인코더 실험을 읽는 법 — A/B/C/D

보정기가 생겼으니 **인코더 개선 효과와 판정 개선 효과를 분리해** 볼 수 있다.

| | 인코더 | 판정 |
|---|---|---|
| A | 현재(step_38000) | 기존 규칙(전사 불일치 · 서비스 규칙) |
| B | 현재 | 보정기(이 문서) |
| C | 새 인코더 | 기존 규칙 |
| D | 새 인코더 | **새 인코더의 margin 으로 다시 학습한** 보정기 |

- B − A = 판정 개선 효과 (이 문서: 같은 지적 수에서 P +9.1%p · R +5.2%p)
- C − A = 인코더 개선 효과
- D − C = 새 인코더에서의 판정 개선 효과
- D − A = 최종 개선

**D 에 옛 보정기를 그대로 쓰면 안 된다** — margin 분포가 바뀌어 임계값이 의미를 잃는다.
D 도 이 문서와 같은 select → final 절차를 따른다.

## 8. 서비스에 붙일 때 (지금은 하지 않음)

1. `mdd_calibrator.load(path)` → 없으면 None → 기존 규칙 유지.
2. `states(canon, margins, site_gops, utt_feats, transcription_mismatch)` —
   서비스 경로는 이미 margins(`gops_m`)·site_gops(`gops`)·utt_feats 를 계산하고 있다.
3. `utterance_advice(states)` 로 발화 안내를 고른다.
4. 같은 녹음을 두 규칙으로 돌려 대조하고, **다른 포트에서** 먼저 띄운다(CLAUDE.md).

라이브러리 판정은 스크립트의 벡터 계산과 표본 9,101자리 전부 일치함을 확인했다(float32 로 통일한 뒤).

## 재현

```bash
source tools/env.sh
A=$MDD_OUTPUTS/analysis/mdd_calibrator
export HF_HOME=/data/speech-ai/corpus/weights/external PYTHONPATH=/data/speech-ai/tools/hf_py38:$PYTHONPATH
# 학습용 margin 특징 (GPU, 약 48분 · 이미 있음)
$PY tasks/pronunciation-assessment/scripts/score/extract_gop_feats.py --split train --n 200000 \
  --hf-ckpt $SPEECH_AI_DATA/checkpoints/w2vbert_stage2/step_38000 \
  --manifest $MDD_OUTPUTS/manifest_tag_rebuilt --out $MDD_OUTPUTS/score_phoneme/gop_margin_train200k.jsonl
# select — 4개 묶음 학습 · valid 에서 선택 · 잠금 (CPU, 약 2분)
$PY tasks/pronunciation-assessment/scripts/score/train_mdd_calibrator.py select \
  --gop $MDD_OUTPUTS/score_phoneme/gop_margin_train200k.jsonl --manifest $MDD_OUTPUTS/manifest_tag_rebuilt --split train
# final — test 한 번 (이미 실행함. 다시 하려면 --force 와 그 이유를 기록할 것)
$PY tasks/pronunciation-assessment/scripts/score/train_mdd_calibrator.py final \
  --gop $MDD_OUTPUTS/score_phoneme/gop_margin_test.jsonl --manifest $MDD_OUTPUTS/manifest_tag_rebuilt --split test
```

산출물 `$MDD_OUTPUTS/analysis/mdd_calibrator/`:
`select_report.json`(분할·묶음별 valid 결과·재녹음 기준 비교·선택 근거) ·
`calibrator_{full,full_mism,tiny,minimal}.joblib` · `mdd_calibrator.joblib`(잠근 것 = full) ·
`final_test.json`(test 1회 결과·유형/위치/쌍별 분해) · `_v0_threshold_on_test/`(폐기한 첫 버전).
