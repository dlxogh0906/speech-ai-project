# 23 — 긴 녹음 1개를 나눠 합산 vs 문장 3개 합산 (2026-10-04)

**결론**

- **긴 녹음 1개를 3등분해 합산해도, 문장 3개를 따로 녹음해 합산한 것과 같다.** 1위 정답 0.865 vs 0.868 로, 차이는 잡음 범위다.
- **자르는 위치는 상관없다.** 같은 길이로 3등분한 것(0.865)과 쉼에서 자른 것(0.863)이 같다.
- **긴 녹음을 통째로 한 번 넣는 것은 약간 낮다** (0.850).
- **지금 서버에 긴 파일을 그냥 보내면 더 낮다** (0.841). 서버가 앞 12초만 보기 때문이다. NPU 모델도 12초 고정이다.
- **성능을 정하는 건 문장 수가 아니라 말한 총 길이다.** 이 시험에서 긴 녹음 길이의 중앙값은 17초다.
- **서빙과 같은 무음 정규화를 켜면 전체가 3~4점 낮아진다.** 1문장 0.733, 3문장 0.837 이다. 하지만 방법 사이의 차이는 같다.
  - 테스트 페이지에 적은 77·86·88% 는 무음 정규화 없이 모델만 잰 값이다(결과 21).

## 실험

- **긴 녹음 만들기**: 같은 화자의 시험 문장 3개를 무작위로 골라 이어 붙였다.
  - 각 문장의 앞뒤 무음은 말소리 기준 0.15초씩만 남겼다. 그래서 문장 사이 쉼은 약 0.3초다.
- **규모**: 웹마이크 외국인 시험 화자 983명 × 2회 = 1,966묶음.
- **길이**: 긴 녹음은 중앙 17.2초다 (10~90% 구간 10.3~24.8초). 81% 가 12초를 넘는다. 3등분한 조각은 중앙 5.7초다.
- **모델**: run_zeroth 단독이다. 한국인 게이트는 쓰지 않았다.
- **채점**: 화자 1명 = 1표, 1위 / 5위 안 정답이다.

## 해석 · 한계

- **이 실험은 짧은 문장 3개를 한 번에 이어 읽은 것에 가깝다.**
  - 실제로 아주 긴 한 문장을 읽으면 문장 끝 억양이 1번뿐이고, 숨 쉬기와 더듬기가 생긴다.
  - 그래서 실험 조건과 같은 설계는 "짧은 문장 2~3개를 한 화면에 이어 보여 주고 한 번에 녹음"이다.
- **3등분이 통째로보다 나은 이유는 확실치 않다.**
  - 학습 때 12초 안의 발화만 봤기 때문일 수 있다.
  - 다만 무음 정규화를 켜면 통째로가 오히려 약간 높아서(0.846 vs 0.835), 둘의 차이는 1~2점 안이다.
- **긴 녹음 방식을 쓰려면 서버가 직접 나눠야 한다.**
  - 지금 `/predict` 는 앞 12초만 보고, NPU 모델도 12초 고정이다.
  - 따라서 서버가 파일 1개를 받아 3등분하고, 조각마다 판정한 뒤 합산해야 한다.

## 서빙 그대로의 정확도 — 테스트 화면에 적는 값

위 표들은 모델 출력만 본 값이다. 서빙은 여기에 몇 단계가 더 붙는다.

- 주 모델에는 무음 정규화한 입력을 넣는다.
- 확인 모델(기존 배포 모델)에는 원본 입력을 넣는다.
- 게이트 τ0.9 를 적용하고, 말소리가 1초 미만인 발화는 거절한다.
- 여러 입력은 log 확률 평균 뒤에 게이트를 건다.

이 단계를 그대로 재현해 다시 쟀다(`serving_sim.py`). 채점은 화자 1명 = 1표다.

| 방법 | 외국인 1위 / 5위 안 | 외국인을 한국인으로 판정 | 한국인 원어민 → 한국 | 외국인 화자 · 한국인 화자 |
|---|---|---|---|---|
| 문장 1개 | 0.730 / 0.940 | 3.2% | 100% | 1,007 · 77 |
| 문장 3개 따로 | 0.832 / 0.972 | 2.0% | 100% | 983 · 77 |
| 문장 5개 따로 | 0.851 / 0.974 | 1.9% | 100% | 972 · 77 |
| **긴 녹음 1개 → 서버 분할(`/predict_long` 규칙)** | **0.829 / 0.972** | 2.0% | 100% | 983 · 77 |

- **모델 단독 값보다 1위 정답이 3~4점 낮다.** 차이 대부분은 무음 정규화에서 온다(위 두 표 비교).
  - 무음 정규화는 한국인 원어민이 브라우저로 녹음해도 한국으로 나오게 하려고 넣은 처리다(결과 11).
- **긴 녹음 서버 분할은 서빙에서도 문장 3개 따로와 같다** (0.829 vs 0.832).
- **합산하면 외국인을 한국인으로 잘못 판정하는 비율도 줄어든다** (3.2% → 2.0%). 한국인 원어민은 모든 방식에서 100% 한국으로 나왔다.
- **실험 규모**
  - 서버가 거절할 발화(0.5초 미만, 말소리 1초 미만) 147개는 뺐다.
  - 긴 녹음은 2,120개(한국인 포함)이고 길이 중앙값은 17.1초다. 3구간 2,013개, 2구간 97개, 1구간 10개다.
- **테스트 화면 표기**: `/multi` 는 1위 73·83·85%, `/long` 은 1위 83%·5위 안 97% 로 적었다.

### 5문장을 한 번에 읽고 5구간으로 나누기 (`serving_sim_long5.py`, 같은 문장 5개끼리 비교)

| 방법 | 외국인 1위 / 5위 안 | 외국인을 한국인으로 판정 | 한국인 원어민 → 한국 | 외국인 화자 · 한국인 화자 |
|---|---|---|---|---|
| 문장 5개 따로 | 0.846 / 0.973 | 2.3% | 100% | 972 · 77 |
| **문장 5개 한 번에 → 5구간** | **0.848 / 0.976** | 2.4% | 100% | 972 · 77 |

- **5개를 한 번에 읽어도 따로 녹음한 것과 같다.**
- **녹음 길이**: 중앙 28.2초다 (10~90% 구간 18.0~39.4초). 60초를 넘은 녹음은 없다.
- **구간 수**: 2,098개 중 2,026개가 5구간이었다. 짧은 녹음은 구간 3초 하한에 걸려 4구간 58개, 3구간 12개, 2구간 2개가 됐다.
- **"문장 5개 따로" 값이 위 표(0.851)와 조금 다른 이유**: 여기서는 화자당 문장 5개 묶음을 2개만 뽑았다(위 표는 20개).

## 적용 (2026-10-04) — `POST /predict_long` · 테스트 화면 `GET /long`

`deploy/nationality-kd-demo/app.py` 에 붙였다. 기존 `/predict` · `/predict_multi` 동작은 그대로다.

- **입력**: 한 번에 이어 읽은 녹음 1개(`audio`)다. 최대 45초까지 읽는다(`KD_LONG_MAX_SEC`). `/predict` 는 12초까지만 읽는다.
- **나누기**: 같은 길이로 기본 3구간으로 나눈다(`KD_LONG_PARTS`).
  - 구간이 3초보다 짧아지면 구간 수를 줄인다. 예: 7초면 2구간, 2.5초면 1구간.
  - 구간이 12초(NPU 고정 길이)를 넘으면 구간 수를 늘린다. 예: 40초면 4구간.
- **구간 판정**: 말소리가 1초 미만인 구간(긴 쉼)은 건너뛴다. 남은 구간마다 `/predict_multi` 와 같은 처리를 한다.
  - 처리 순서는 무음 정규화 → 주 모델 → 확인 모델(원본 구간) → log 확률 평균 → 게이트 규칙이다.
- **응답**: `{"n", "sec", "top5", "per_part": [{"label", "prob", "start", "end"}], "gate_korea", "native", "low_confidence", ...}`
- **저장**: 녹음은 저장하지 않는다.
- **테스트 화면 `/long`**
  - 짧은 문장 3~4개로 된 글을 한 단락으로 보여 준다. 8개 중 무작위로 고르고, "다른 글로 바꾸기"가 있다.
  - 한 번 녹음한 뒤 판정한다. 15초 목표 막대를 보여 준다.
  - 3초 미만이면 막고, 8초 미만이면 경고만 한다.
  - 결과는 합산 1~5위와 구간별 1위(구간 시각 포함)다.
- **확인한 것**
  - 실제 시험 녹음 3개를 이어 붙인 17~20초 파일에서 3구간으로 판정했다.
    - 몽골 화자는 구간별로 인도네시아·몽골·몽골이 나와 합산 몽골 0.72 였다. 같은 문장을 따로 합산하면 0.45 였다.
    - 서버 처리는 0.2~0.5초다.
  - 경계 사례도 의도대로 동작했다.
    - 2.5초는 1구간, 7초는 2구간, 40초는 4구간이 된다.
    - 50초는 45초까지만 읽어 4구간이 된다.
    - 가운데 6초가 무음이면 그 구간을 건너뛰고 2구간만 쓴다.
    - 무음뿐이면 `no_speech` 를 돌려준다.
  - 휴대폰 크기 브라우저(가짜 마이크)로 공개 주소에서 녹음부터 판정까지 확인했다. 콘솔 오류는 없었고, 업로드 폴더 파일 수도 그대로였다.
- **열린 곳**: GPU 데모 https://<GPU-funnel-주소>:8443/long
- **NPU**: 운영 8905 에도 반영했다(2026-10-05 15:31, https://<NPU-funnel-주소>/multi · 결과 13 끝). 서버 처리 시간은 3구간 0.6초, 5구간 1.0초다.

### `/multi` 를 한 번에 읽기로 변경 (2026-10-04 저녁)

- **API 변경**: `/predict_long` 이 `parts`(1~10) 를 받는다. 최대 녹음 길이는 60초로 늘렸다(5문장을 천천히 읽어도 잘리지 않게).
  - 구간 길이 규칙(3초 하한, 12초 상한)은 그대로다. 그래서 1문장도 12초를 넘으면 2구간이 된다.
- **`/multi` 화면 변경**: 1·3·5문장 선택은 그대로 두고, 고른 수만큼의 문장을 한 단락으로 보여 준다.
  - 글은 이야기 8개(각 5문장) 중 하나의 앞 N문장이다.
  - 한 번 녹음하면 `parts=N` 으로 보낸다.
  - 목표 시간은 1·3·5문장에 5·15·25초다. 2초 미만이면 막고, 목표의 60% 미만이면 경고만 한다.
  - 녹음 중에는 문장 수와 글을 바꿀 수 없다.
- **표기**: 1위 73·83·85% 로 위 서빙 그대로 값이다(1문장 = 문장 1개, 3·5문장 = 한 번에 읽기 → N구간).
- **예전 화면**: 문장마다 따로 녹음하던 `/multi` 는 `/predict_multi` 와 함께 API 로만 남겼다.

### 다 읽지 않고 보냈을 때 (2026-10-04 밤)

서버는 실제 말한 길이에 맞춰 구간을 줄인다. 예를 들어 3문장 모드에서 5초만 읽으면 1구간으로 판정한다. 그러면 정확도는 1문장 수준이 된다.

녹음 하나를 1구간으로 판정할 때의 길이별 정확도다(서빙 그대로, 외국인 시험 발화, 발화 단위, `serving_sim_utt.npz`).

| 녹음 길이 | 발화 수 | 1위 / 5위 안 정답 |
|---|---|---|
| 4초 미만 | 1,930 | 0.643 / 0.902 |
| 4~5.5초 | 2,274 | 0.735 / 0.938 |
| 5.5~7초 | 4,195 | 0.755 / 0.947 |
| 7~9초 | 851 | 0.763 / 0.967 |
| 9~12초 | 1,037 | 0.798 / 0.971 |
| 12초 이상(앞 12초만 사용) | 1,187 | 0.773 / 0.960 |

이에 맞춰 다음을 바꿨다.

- **화면이 짧은 녹음을 막는다.** 목표의 60%(1 · 3 · 5문장에 3 · 9 · 15초, `/long` 은 9초)보다 짧으면 판정하지 않는다.
  - "글을 끝까지 읽어 주세요 (지금 4.9초 · 최소 9초)" 라고 알리고 다시 읽게 한다. 이전 녹음도 버린다.
- **응답에 두 필드를 더했다.** `parts_requested`(요청 구간 수)와 `voiced_sec`(말소리 길이)다.
- **결과 화면이 줄어든 구간을 알린다.** 녹음은 길었지만 말을 중간에 멈춰 `n < parts_requested` 가 된 경우다.
  - 제목을 "판정 결과 (1구간)" 으로 바꾸고, "말한 시간이 짧아(약 3초) 3구간 대신 1구간으로 판정했어요…" 를 보여 준다.
- **CORS 를 선택 사항으로 붙였다.** `KD_CORS_ORIGINS` 에 등록한 도메인의 웹만 브라우저에서 직접 부를 수 있다. 기본은 꺼짐이다.
- **확인한 것**
  - 테스트 포트와 공개 주소에서 다음을 모두 확인했다.
    - 3문장 5초, 5문장 12초, 1문장 2.5초, `/long` 5초는 모두 막혔다.
    - 3문장 17초는 정상으로 3구간 판정됐다.
    - 5초만 말하고 16초 녹음하면 1구간 판정과 안내가 나왔다.
  - CORS 사전 요청은 등록 도메인만 허용됐다. 업로드 폴더 파일 수는 그대로였다.
- **연동 문서**: `deploy/nationality-kd-demo/연동_가이드.md` 에 웹·앱용 요청·응답, 오류, 길이 기준, 정확도, 예제 코드(JS · Swift · Kotlin), 라벨·ISO 표, 문장 세트를 정리했다.
- **확인한 것**
  - 테스트 포트와 공개 주소에서 1·3·5문장을 각각 6·17·27초 녹음했고, 판정은 1·3·5구간으로 나왔다.
  - 콘솔 오류는 없었고, 업로드 폴더 파일 수도 그대로였다.
